# Tursora — Feature Specification (v1)

> Tursora is a macOS file manager written natively in Swift + AppKit. It brings the interactions that Finder lacks or handles
> poorly — sideways jumps in the location bar, per-tab history, split panes, zoom steps, the filter field — over from KDE Dolphin, while keeping the interface shaped as much like Finder as possible.
> Every section names what it is measured against: **matches Dolphin** means the semantics follow Dolphin, **matches Finder** means the form, the labels and the wording follow Finder,
> and the Finder parts are based only on Finder's own resources (nibs, string tables) rather than on memory — see [research/](research/).
>
> Why Dolphin/KIO was not ported: [audit/PHASE-0-REPORT.md](audit/PHASE-0-REPORT.md). Decision records: [DECISIONS.md](DECISIONS.md).
> Not yet built: [gaps/](gaps/), [ROADMAP.md](ROADMAP.md).

## 0. Scope

Tursora is free to use and the project's source is open under the MIT licence; the README and the product page display the free, open-source and licence entry points prominently. Third-party dependencies keep their own licences, and bundled resources carry the project licence. Published source, installable builds, automated verification and on-device verification are each recorded separately, and unreleased development features are never presented as capabilities of a shipped version.

App icon: two blue glass panes form an abstract tail fin; the light background is cropped to a single rounded plate, with transparency around the edges and at the outer corners, and no added stroke, outer shadow or second plate beneath. The foreground keeps its original proportions and position; the 1024 px export leaves 80 px of margin on each side with a corner radius of 192 px, which is this app's own geometric choice. The app bundle ships macOS icon sizes from 16 to 1024 px, and the `.icns` carries its own transparent outline rather than relying on the system to round the corners. The evidence and the verification status are in the [icon edge record](research/app-icon-edges.md).

**Local filesystem interface.** The file backend goes through `protocol FileProvider`; today there is only `LocalFileProvider`, which can also browse volumes macOS has already mounted. Connect to Server mounts SMB / NFS / WebDAV and similar services through the system's NetFS — see §15 for the details; there is no in-house SFTP backend, no KIO and no KDE dependency.

| Highlight | Why it is worth doing |
|---|---|
| **Location bar** | Finder has no location bar at all by default. Dolphin's breadcrumbs can **jump sideways to sibling folders**, which is the single largest efficiency gap |
| **Tabs** | Finder has them, but without "reopen closed tab" or "per-tab history" |
| **Quick navigation** | Sidebar + Back/Forward/Enclosing folder + history dropdown + Go to Folder |

Not implemented at present: compact view, reading and writing Finder tags, version-control integration and the Services menu. The terminal panel and read-only ZIP browsing are enabled by default and can be turned off in Settings; remote connections use system mounts only.

## 1. Windows, sidebar and quick navigation (matches Dolphin's Places + Finder's sidebar)

**Dock context menu**: offers New Window, Downloads and Applications. All three open a new window and activate the app, going to Home, the current user's Downloads folder and the system Applications folder respectively, without changing existing tabs, split panes, filters or searches. The standard window list, Options, Hide / Quit and so on come from macOS; the evidence for the menu selection and its wording is in the [Dock record](research/dock-menu.md).

**Sidebar** (`NSOutlineView`, source list style):

```
Favourites
  🏠 fxlin
  🖥 Desktop
  📄 Documents
  ⬇︎ Downloads
  …  user entries (drag in, remove, reorder; built-ins can also be removed and reordered, Reset restores them)
Locations
  💽 Macintosh HD
  💾 External volume (ejectable)
```

| Action | Shortcut |
|---|---|
| Back / Forward | `⌘[` / `⌘]`, mouse side buttons 4/5, two-finger or three-finger trackpad swipe |
| Enclosing folder | `⌘↑` |
| Open the selection | `⌘↓` (`Return` is rename — see [DECISIONS.md](DECISIONS.md) D3) |
| Go to Folder… | `⌘⇧G` (enters location-bar editing) |
| Home | `⌘⇧H` |
| **Press and hold** or right-click the Back / Forward button | Pops up the history list, so you can jump several steps at once |

Going Back or Forward returns the pane to where it was, not merely to the folder: the folder you came from is selected again **and** the view is scrolled back to the offset you left it at. The offset is restored whether or not anything ended up selected — selecting a row only brings that row barely into view, which is a different place from where a long list was scrolled to.

The window name follows the active pane's folder (so the Window menu and accessibility can identify it); the title bar hides the name and no longer repeats the path, and the folder location is shown by the editable location bar. The sidebar button is pinned to the far left of the toolbar, and collapsing the sidebar does not move the window; the sidebar and the content area share a flat seam, and only the outer window keeps rounded corners. Favorites icons all use an 18 pt image area. The status bar shows "N items / N of M selected", with the zoom slider on the right (Dolphin's position).

**Folders tree**: View → Show / Hide Folders, `F7` by default (customisable), opens a separate folder tree below Places on the left, with a draggable height divider between the two panels. It is hidden the first time; opening it keeps Favorites / Locations, and a collapsed sidebar is expanded first. The tree follows the active tab and the active pane; list / icon mode, filtering, grouping and search do not filter the tree itself. Inside a ZIP it follows the folder holding the original ZIP and never shows the temporary copy.

- Clicking a folder navigates the currently active pane; right-clicking captures the folder that was clicked and offers Open, Open in New Tab and Open in Other Pane. The last of these creates or reuses the other side under the existing rules. Dropping onto a tree node goes through the same copy / move tasks and the same undo chain; the view never reads or writes the filesystem directly.
- Only browsable folders are shown; ordinary files and packages are not listed. One level of children is read in the background on demand, and following the active location expands only the ancestor chain of the target; the whole disk is never pre-scanned recursively. Load errors appear inline at the bottom of the tree and can be retried with Refresh Folders; closing the tree or collapsing the sidebar stops the watchers and stops results from being applied.
- Accessibility reading the tree, or asking whether a node can be expanded, changes no node state and triggers no directory read; only an actual expand action or following the active path loads the nodes it needs. After an expand or a refresh completes, the selected folder stays fully visible, and an unrelated refresh does not yank the view back while another branch is being inspected by hand.
- The menu offers Show Hidden Folders (off by default), Limit to Home Directory (on by default) and Refresh Folders. When limited to Home, Home is the root as long as the active location is inside Home; a location outside Home still switches the root to `/` so the tree can follow. The tree's hidden-items option is independent of the file pane's. To follow macOS system aliases such as `/tmp` and `/var`, the model resolves the real path in the background and shows the `/private/...` ancestors; it adds the hidden `/private` root node only for the current path, and neither opens other hidden folders nor rewrites that option.
- The session saves each window's tree visibility, its top/bottom ratio and these two options; the set of expanded nodes is not saved across processes, and on reopening the tree expands again from the active location. In Dolphin, Places and Folders are separate panels; this implementation settles on stacking them on the left, with no arbitrary docking, floating or panel locking — see the [folder tree comparison](research/folder-tree.md).

## 2. Location bar (matches Dolphin; the core differentiator)

```
  ◀  ▶  ▲   [ 🏠 fxlin ▸ Workspace ▸ Tursora ▸ app ]        🔍
                 └ every segment clicks   └ ▸ opens that level's sibling folders
```

- Breadcrumb mode: each path segment is its own button and clicking it jumps straight there; **clicking the `▸` between segments opens the list of sibling folders at that level**, so you can jump sideways.
- Clicking the empty area, `⌘L` or `⌘⇧G` switches to an editable text field; `Esc` returns to the breadcrumbs.
- Editing mode: **inline completion** (the completed part is selected, so typing on replaces it; Tab or → accepts it) plus a candidate list panel (↑↓ to select, Return to accept and navigate, Esc to close, click to select). Completion skips packages (.app).
- An over-long path collapses from the **left**, keeping the first segment; over-long segments are compressed.
- Narrow windows and split panes always keep the root folder, the collapsed-path entry point and the trailing folder menu, shortening the text where necessary; resizing the window repeatedly causes neither a persistent layout loop nor blocked navigation.
- The current folder's segment is highlighted; other segments only show a background on hover.
- Every pane has its own location bar above its file area; in a split view both paths are shown at once and each lays out to its own width. Clicking a path, a breadcrumb or a completion first activates that pane, and the jump changes only that pane's folder. `⌘L` / `⌘⇧G` edit the active pane's path.
- Switching pane or tab dismisses the path editor and the completion panel on the side you left without committing uncommitted input; a path action that has already been captured cannot be redirected at the newly active pane. The other side's path, navigation history, filter and search stay independent.

## 3. Tabs (matches Dolphin)

| Interaction | Shortcut |
|---|---|
| New / Close / Reopen closed | `⌘T` / `⌘W` (closes the window on the last tab) / `⌘⇧T` |
| Next / Previous | `⌃Tab` / `⌃⇧Tab`, `⌘⇧]` / `⌘⇧[` |
| Go straight to tab n | `⌘1` … `⌘9` (`⌘9` = the last one) |
| Middle-click a tab | Closes it |
| Middle-click or `⌘`-double-click a folder | Opens it in a background tab |

- Each tab holds its own current folder, navigation history, selection, scroll position and filter; in a split view each of the two panes has its own set. Mode, sort, zoom, grouping, hidden items and previews are saved under §5's folder policy and restored on entering a folder.
- The tab bar uses a neutral base strip, a soft selected surface and centred titles; hovering reveals the close button without shifting the text. A tab grows to 240 pt and stops, the way a browser's does, instead of stretching to the window edge; the cap is soft, so a title that needs more room takes it, up to 480 pt, as long as the strip can spare it and every tab keeps the same width. When the tabs do not fill the strip the new-tab control sits just after the last one rather than at the far edge, and it returns to the trailing edge as soon as they do fill it (D79). Many tabs keep a readable width, and once they overflow the bar scrolls horizontally and offers a text menu of every tab, scrolling the chosen one into view. The app follows the system light / dark appearance, and switching while it is running also refreshes the tabs, the completion panel, the active-pane line and the task card borders; [design evidence and verification](research/tabs-and-appearance.md).
- Tabs can be dragged to reorder; the tab bar is always shown, so even a single tab displays the split titles and offers the context menu. This is Tursora's own default; Dolphin offers a setting for whether the bar auto-hides.
- A single-pane tab shows the folder name; a search shows `Search: <name condition>`, or `Search Results` when there is no name condition. A split tab shows both sides at once in physical left-to-right order, separated by a hairline rule the strip draws down the full height of the tab rather than by a `|` character in the text (D78). The two names are laid out as separate fields, so each truncates on its own and a short name is never shortened beside a long one; switching the active side does not change either of them, and the active pane is identified by the indicator line in the content area. Where one string is still needed — the Rename Tab sheet and the All Tabs menu — the halves are joined as `Left | Right`. The tab's own tooltip is unchanged and keeps showing each pane's full path, and a saved session stores only a custom name you typed. VoiceOver reads the two names separated by a comma, because a drawn rule reads as nothing. A custom tab name overrides the automatic title and clearing it restores the automatic one; the full path is kept in the tooltip, and a ZIP shows its logical path.
- **Dragging files onto a tab** (as in Dolphin): hovering for 800 ms switches to that tab automatically; dropping on a tab drops into that tab's current folder (a move within a volume, a copy across volumes or with `⌥`); dropping on empty space in the tab bar opens one background tab per folder.
- Closing and then reopening a tab restores the split state, both panes' histories and the custom name together. Closing a background tab, or closing several at once, keeps the active tab if it still exists; a neighbouring tab is selected only when the active one was closed.
- A new pane waits until the parent controller has wired up its callbacks before performing its initial navigation; if another location has been chosen explicitly in the meantime, the late initial navigation must not override it.
- On launch the windows, tabs and split panes of the last workspace are restored by default; §22 covers the full scope, the persistence and the semantics of the off switch. `⌘⇧T` restoring the full object of a closed tab while the app is running and rebuilding a session after a quit are two separate behaviours.

The tab context menu follows Dolphin and offers **New Tab, Detach Tab, Rename Tab, Close Other Tabs, Close Tabs to the Left, Close Tabs to the Right, Close Tab**. Each command targets the tab that was actually right-clicked, not an index resolved after the menu closes and not the current tab; right-clicking does not itself switch tabs. Close Other Tabs is disabled when there is no other tab, the corresponding bulk-close item is disabled at the left and right edges, and Close Tab on the last tab closes the window.

- **New Tab**: creates and activates a single-pane tab at the location of the target tab's active pane; a search re-runs its request rather than copying the old results. `+` and `⌘T` do the same thing for the current tab; a folder's Open in New Tab still opens the folder named explicitly. Disabled while the active side is preparing a ZIP.
- **Detach Tab**: reopens the target tab's one or two logical locations in a new window and then closes the original tab; the left-to-right order, the active side, the custom name and the search request are preserved, while navigation history, selection, filter, scroll position, file tasks and the undo stack are not migrated. Disabled while either side is preparing a ZIP. File tasks continue to belong to the original window; closing that window still cancels its tasks and waits for cleanup.
- **Rename Tab**: changes only the tab's name, never the folder name on disk; an empty name restores the automatic title.

The pinned source references, the menu order and the design boundaries are in [pane location bars and tab actions](research/pane-paths-and-tab-actions.md).

## 4. Split panes (matches Dolphin)

The structure matches Dolphin's (`DolphinTabWidget` → `DolphinTabPage` → primary/secondary `DolphinViewContainer`): **tabs are the outer layer, and each tab holds 1–2 side-by-side panes**.

| Interaction | Behaviour |
|---|---|
| Toolbar Split View / `⌘⇧D` | Not split: opens a second pane on the right (same folder) and activates it. Already split: closes the **active** pane (the menu item and the button tooltip spell out Close Left / Right Pane) |
| Click any pane (including its location bar) | Activates it; a 3 pt accent-coloured line along the top identifies the active pane; each side's location bar keeps its own path, while the window title, the sidebar highlight and the toolbar filter field follow the active pane |
| `⌥⇥` | Moves focus to the other pane |
| Right-click a folder → open in the other pane | Not split: splits and shows that folder. Already split: the other pane navigates there and is activated |
| `⌘⇧C` / `⌘⇧M`, context menu | Copy / move to the other pane |
| **Drag a tab into the content area** | Release over the left or right third (a translucent highlight shows where) and that tab becomes the current tab's left or right pane; releasing over the middle cancels |

The toolbar's split button shows the current tab's split state, and switching tab or activating the other pane immediately syncs both its selected state and its close target; the button performs the same action once it has been collapsed into the overflow menu. Open in Other Pane on a sidebar place hands that place to the other pane: when not split it creates a second pane, and when already split it navigates the other pane there and activates it, leaving the original pane's folder alone. Open in New Tab and Open in Other Pane in the sidebar menu capture the place that was actually right-clicked rather than the row index resolved after the click, and they do not navigate the original pane first; right-clicking a section header or empty space produces no menu.

## 5. View modes, zoom and previews (matches Dolphin)

| | List (details) | Icons | Columns |
|---|---|---|---|
| Implementation | `NSOutlineView`, folders expand in place (▸) | `NSCollectionView` grid, top level only | `NSBrowser` in item mode, as in Finder; a selected folder opens the column to its right |
| Zoom steps | 16 / 22 / 32 / 48 / 64 (row height follows, 24→72) | 32 → 512, 12 steps | The list's ladder, remembered separately; the default step gives Finder's 24 pt row |
| Previews | At icon sizes ≥ 32 a content thumbnail replaces the type icon | Same as on the left (previews from the 64 default upward) | Rows show the type icon; a selected file is previewed in the last column |

- Switching: the segmented control on the right of the toolbar, `⌘⌥1` for icons, `⌘⌥2` for list and `⌘⌥3` for columns (`⌘1…9` belong to tabs; Finder binds `⌘3` to columns).
- Columns: **selecting never navigates.** The pane's location stays the folder in the first column; selecting a folder opens its contents in the next column, and only opening it (double-click, ⌘↓; Return renames, as in every view) moves the location, so Back, the path bar, the window title and the terminal all keep referring to the column root. This differs from Finder, where the deepest selected folder becomes the location (D84). The last column shows a selected file with the preview pane's renderer — Markdown as rich text, everything else through Quick Look. Filtering and sorting apply to every column; grouping is a list and icon presentation and is not drawn in columns. Column widths default to Finder's 245 pt, resize by dragging, and never go under 100 pt. Deselecting clears a selected file but leaves the folder rows selected, since those are what hold the columns open; after a selected file is deleted, its folder stays selected and its column stays open. Navigating elsewhere starts over with one column and nothing selected, even when the destination contains the chain you were in.
- Zoom: `⌘`+scroll wheel, trackpad pinch, `⌘+` / `⌘-` / `⌘0`, and the slider on the right of the status bar.
- Previews toggle with `⌃⌘P` (they held `⇧⌘P` until the preview pane took it, D82); thumbnails are cached by path, point size, screen scale, modification time and file size, are requested only for visible items, and types with no thumbnail are remembered so they are not retried. After a zoom, a reload, a cell being reused or previews being turned off, a late request from earlier must not overwrite the current icon.
- Plain text, source code, Markdown, JSON / XML and the like show a real snippet from the start of the file on a 3:4 light paper surface in a 7–10 pt monospaced face; zooming in shows more content instead of shrinking a whole page of text into illegibility. At most 64 KiB is read in the background and 8,192 characters are laid out, with support for UTF-8 and for UTF-16 with a BOM; unsupported formats and encodings fall back to Quick Look, and when no preview is available the type icon is used. List and icon views use the same code path; the paper is document content, so it stays light in both light and dark themes, and there is no syntax highlighting. At 32 pt the point is still to recognise the kind of text — zoom in or use Quick Look to read more; [comparison and implementation](research/text-thumbnails.md).
- Mode, sort field and direction, the separate zoom step of each of the three views, the grouping field and the field last enabled, hidden files and the preview toggle all persist under the folder policy. They are restored on leaving and coming back, in a new tab, in a new split pane, and on opening the same folder again after a restart; folders with no record use the separately saved defaults. A new pane must mount the real view for the corresponding mode.
- The toolbar's view button always reflects the active pane; it syncs immediately after a menu or keyboard switch, and a background pane changing mode does not affect the current toolbar.
- Icon view: multiple selection and rubber-band selection, arrow keys, `Return` to rename (preselecting the base name), `Space` for Quick Look, drag and drop (dropping onto a folder icon drops into it), and a context menu identical to the list's.
- Sorting: Name / Date Modified / Date Created / Date Last Opened / Date Added / Size / Kind (labels as in Finder's `ArrangeByMenu.nib`), ascending or descending, ties falling back to name (name order flips with the direction). Folders lead only under Name, the one case Finder's "Keep folders on top: In windows when sorting by name" covers; under every other key they take part in the sort like files, so a folder modified between two files appears between them (D76). Items with "no date" under the three new date keys sort last in both ascending and descending order; `Date Modified` keeps its old semantics. The three entry points agree: View ▸ Sort By, the Sort By context menu, and clicking a list column header. The icon view has no columns and only follows the sort key.
- Optional list columns: Date Modified / Date Created / Date Last Opened / Date Added / Size / Kind, in the order of "Show Columns:" in Finder's `ViewOptionsWindow.nib`. Name is always shown; Location appears only in search results and is always the last column. Date Modified / Size / Kind are shown by default and the rest are hidden. Right-click the header to tick columns on and off, and click a header to sort by that column. The set of visible columns is remembered per folder alongside the other view properties and takes part in "Use Current Settings as Default" and "Restore This Folder to Default"; column widths are not persisted.
- Folder sizes: for folders the Size column shows the item count ("1 item" / "N items", Finder's `I_ITEMS_*` wording) instead of `--`. Turn on `Calculate all sizes` (View ▸ Folder View Settings, or the header context menu; off by default, remembered per folder) and it shows the recursive byte count instead, formatted exactly as for files. The calculation runs in the background: the item count from a single directory read, the byte count from a recursive enumerator that skips symlinks, ignores errors and gives up beyond 500,000 items. Results are cached by (path, modification time) and invalidated — together with every ancestor already measured — when `DirectoryChanges` arrives. Sorting by Size uses whatever calculated value is known for a folder and re-sorts automatically as new values arrive. Leaving the folder cancels immediately, and late results are never shown in the new folder. ZIP listings and search results only count items and do no recursive traversal.
- The list's Name column has a minimum width of 180 pt, so a narrow split pane still reserves room for filenames and the date, size and kind columns cannot squeeze them down to illegibility.
- Show all filename extensions in Settings is on by default; turn it off and file and package names in every file view hide their last extension, while ordinary folder names are unchanged. This changes only the displayed label; filtering, sorting, paths and renaming still use the full real name. Existing and new windows, every tab and every split pane update together.

### Per-folder memory and one shared default

- The default is **Remember Each Folder** (per-folder memory); both **Folder View Settings** in Settings and **View → Folder View Settings** can switch to **Use One View for All Folders** (one shared default). Switching to the unified policy uses the existing defaults and does not automatically promote the current pane to be the default. Switching back to the per-folder policy keeps the folder records made earlier.
- **Use Current Settings as Default** deliberately saves the current folder's whole set of settings as the default; folders that already have customisations keep them, and folders with no record follow the new default. **Restore This Folder to Default** deletes the current folder's customisation, switches to the default immediately and keeps following the default afterwards; it is available only for ordinary folders under the per-folder policy.
- Under the per-folder policy an ordinary change does not live-update another open pane showing the same folder; that pane picks up the latest record the next time it enters the folder. When both panes make changes deliberately, the whole property set from the last change becomes the saved value. Policy switches, default changes and restore-to-default do sync the affected open panes on ordinary folders; under the unified policy an ordinary change updates the shared default.
- Filter text, selection, scroll position and history are not written into the folder record and are not passed to a new tab or to the other pane. Restoring properties neither writes back nor navigates again; properties are read from the in-memory store before the listing loads, and asynchronous listings and archive loads continue to use the navigation generation to stop A's late results from overwriting B's. The menus, the toolbar's mode and grouping state, the sort arrow and the zoom slider follow the active pane after the restore.
- The store lives at `~/Library/Application Support/Tursora/DirectoryViewProperties.json`. It writes no `.directory`, `.DS_Store` or xattr into the browsed folder and does not require that folder to be writable. The v1 JSON keeps the policy, the defaults and the folder records separate; consecutive changes are coalesced into one atomic replacement, and the app waits for pending writes to finish on quit. An unsupported version or a corrupt file falls back to usable defaults, and neither reading nor quitting without changes overwrites the original file; only a real change afterwards replaces it with the current format. A single known field that is wrong falls back to the factory value, an out-of-range zoom is clamped to a valid step, and a bad folder record is skipped on its own. A failed save does not block the operation that triggered it; Settings shows the reason inline together with Retry Saving View Settings, and a successful retry clears the error, with no modal alert.
- An ordinary local file URL is keyed by an absolute path that has been normalised and had its symlinks resolved; trailing slashes, the query and the fragment are ignored, and case is not folded wholesale. A file URL on a non-local host, and any non-file URL, has no folder key. The key is fixed at navigation time and later changes use that key; when a symlink is repointed at a new target, a refresh or Reload notices the key change, clears the old target's filter, selection, scroll position and pending rename, and then restores the new target's settings. Symlinks are resolved when enumerating a directory, while entries and history keep the spelling of the requested path. The browser does not currently resolve Finder aliases automatically; the target's record is shared only when the caller has already supplied the target folder. After a rename or a move the lookup uses the new path and inodes are not tracked, so a reused old path, or a volume reusing the same mount point, may inherit the old record, while the same volume at a different mount point does not follow.
- ZIP and search-result views are not persisted. Every navigation into a ZIP's root or an inner folder takes the defaults as they stand at that moment, and changes made then affect only that pane; a search inherits the view of the pane it started from, and changes to mode, sort, zoom, grouping, hidden items and previews made during the search last only until the search is left. Neither responds to ordinary-folder policy, default or reset notifications, and neither can set the current view as the default or reset the folder it came from. A ZIP's logical address and the temporary extraction path must never be written into the folder store; a search keeps the context of the folder it came from so it can return there, but writes neither that folder's record nor the shared default. Returning to an ordinary folder re-reads that folder's currently saved values, and the archive's read-only operation boundary is unchanged.
- The folder-view store does not restore windows, tabs or history; windows and tabs are restored by §22's separate session store, and navigation history is still not persisted. Settings are not applied recursively to subfolders, and there is no equivalent of Finder's full Show View Options dialog. The pinned Dolphin source references and the storage trade-offs are in the [per-folder view research](research/directory-view-properties.md); the automated and on-device verification for the corresponding version is in the [folder view verification record](research/computer-use-2026-09-12-directory-views.md).

## 6. File operations (semantics match Finder)

| Operation | Behaviour |
|---|---|
| `⌘C` / `⌘X` / `⌘V` | Cut items are drawn translucent; the cut state is global (cut in one tab, paste in another); pasting into the same folder produces a " copy" duplicate |
| `⌘D` | Duplicate: "name copy.ext", "name copy 2.ext" |
| Rename (single item) | `Return`; or click the text of a row that is already selected and is the only selection, and it begins after one system double-click interval (a double-click, a selection change, pointer movement past the drag threshold, or a drag session starting or ending all cancel it). The part without the extension is preselected; case-only renames work on APFS |
| Batch rename (2 or more items selected) | File ▸ `Rename N Items…`, the same item in the More menu, or the context menu opens a Finder-style sheet (not a modal dialog): the three modes `Replace Text` / `Add Text` / `Format`, with a live preview of each item's new name |
| `⌘⌫` / `⌘⌥⌫` | Move to Trash (visible in Finder, can be put back) / Delete Immediately (with confirmation) |
| New Folder `⌘⇧N` | "untitled folder", "untitled folder 2", selected after creation |
| Drag and drop | Same volume = move, across volumes = copy, `⌥` = copy, `⌘` = move (a move even across volumes); dropping onto the folder an item is already in, or onto itself, does nothing; you can drop onto Finder, sidebar favourites, the folder tree, a tab, a breadcrumb segment or the other pane; drag and drop works across tabs |
| Quick Look | `Space` / `⌘Y`, arrow keys move between items inside the panel |
| Undo / Redo | Covers rename, batch rename, move, copy, duplicate and Move to Trash; each operation (a whole batch counting as one) forms its own undo group, tracked per window |
| Open With | Context submenu: the default application first, the rest by name |
| Other context items | Open in New Tab / New Window / Other Pane, Copy / Move to Other Pane, Show in Finder, Copy Path, Add to / Remove from Favourites |

### Spring-loaded folders and breadcrumb drops (matches Finder)

Hovering a drag over a folder opens it automatically after the system spring delay (the global key `com.apple.springing.delay`, timed by AppKit — Tursora runs no timer of its own): in list and icon views the current pane navigates into it, a sidebar place becomes selected, and a folder-tree node expands in place without navigating. Springing only happens where "the drop would have been accepted anyway", and never on files, read-only panes, archive locations, the dragged object itself, or the folder the dragged object is already in. Finder rolls back the windows it sprang open once the drag leaves; Tursora does not roll back.

Every **visible** breadcrumb segment is a drop target, judged by the same single rule as the list, the icon view, the sidebar, the folder tree and the tab bar; the target is the folder that segment points at, and it highlights on hover. Segments folded into the `…` overflow menu are not targets, and while the path text field is open the whole bar accepts no drops. The evidence and what remains inferred are in the [drag and drop record](research/drag-and-drop.md).

### Batch rename (matches Finder's "Rename Finder Items")

With two or more items selected, the rename item in the File menu, the More menu and the context menu becomes Finder's plural wording `Rename N Items…` and opens a sheet attached to the current window; `Return` and clicking a name are still single-item inline renames and do not open the sheet.

- **Replace Text**: `Find:` / `Replace with:` replaces every occurrence across the whole name including the extension, so the extension can be changed; an empty `Find` changes nothing.
- **Add Text**: the text plus `Where:` (`after name` / `before name`) changes only the base name and keeps the extension.
- **Format**: `Name Format:` is `Number` or `Date`. Under `Number`, `Custom Format:` is a pattern in which one run of `#` is replaced by the sequence number and the length of the run sets the leading zeros, so `Photo ###` gives `Photo 001`, `Photo 002`; the run may sit anywhere, and a number wider than the run is never shortened. A pattern with no `#`, or with more than one run, is not a placeholder: the number is added at the end (or the start, per `Where:`) so that a batch can still apply. `Start numbers at:` sets the first value and a hint under the field states the rule. Under `Date` the item's own modification time is used, in the form `2026-09-13 at 14.02.03`, positioned by `Where:`, and `Start numbers at:` is hidden. Either way the base name is rewritten and the extension kept.

The window shows `Example:` and a line-by-line "old name → new name" preview that updates on every keystroke. When a name is empty, contains `/` or `:`, is duplicated within the batch, or collides with an existing item in the **same folder** that is not part of the batch, `Rename` is greyed out and the reason is shown in place (wording taken from Finder). A name the batch itself is giving up does not count as taken, so chains (a→b while b→c), swaps and case-only changes can all be carried out: when writing to disk, each item is first renamed to a unique temporary name in the same folder and then to its target name; if any step fails the whole batch rolls back, and a file outside the batch with the same name is never overwritten. The whole batch counts as one undo group, so `⌘Z` reverts every name at once and redo applies them again; after the rename the originally selected items stay selected, and other panes and Info windows follow the new names item by item. It applies in list and icon views, in split panes, across tabs, and with filtering and grouping active; search results are renamed by URL and each stays in its own folder. The evidence, the inferred parts and the boundaries are in the [batch rename research](research/finder-batch-rename.md).

Copy, move, Duplicate, clipboard operations and drag and drop are unified into standalone file-operation tasks; copying or dragging out of a read-only ZIP tab still only reads the source archive, and copying into a writable folder uses the same task engine. List and icon modes share the same entry points, and a task fixes its sources, its destination and the originating window's undo stack the moment it starts, so switching tab, pane, filter or grouping does not change the transfer's destination.

A longer task shows the **File Operations** window automatically, and it can also be opened from **Window → File Operations**; a quick failure also brings it up, new tasks are listed first, and a conflict scrolls to the task it belongs to. Each entry shows the current item, bytes transferred out of the total, transfer speed, estimated time remaining and status, with Pause / Resume / Cancel. Once a task reaches a terminal state — completed, failed or cancelled — the progress bar and the current-item line are hidden, because a bar there reads as work still in flight; the state, the byte total, the completed and skipped counts and any errors stay (D77). A pause shows Paused only once the worker thread has confirmed it; a single large file can also be paused and cancelled mid-transfer. The byte count covers ordinary file data, while resource forks, extended attributes and the like are finished in the metadata phase; the total is unknown while the preparation scan runs; and the atomic rename of a same-volume move, the metadata finalisation and the publish phase show the real phase rather than invented byte progress and ETAs.

A copy is written first into private staging on the destination volume and published only after it has fully succeeded. Replace keeps the original destination until the publish succeeds; cancelling or a failure cleans up the unfinished staging and does not list it as a successful item. A cross-volume move removes each source only after the corresponding destination is complete; a directory merge records the child items that actually succeeded and never counts an already-existing destination directory as created or moved wholesale. Completed, cancelled, partially completed and failed are each shown separately; undo records only the changes that really succeeded, keeps Replace's original destination and the restore content for cross-volume moves, and redo does not need to read the source files again. That restore content occupies disk space for as long as the undo history lives. If undo or redo fails — because path identity changed, for instance — the restore directory is kept until it is restored or cleaned up by hand and the error message gives the path; the copies are not deleted even when the undo action is consumed or the window closes. When a cross-volume move's restore copy or its destination is modified after the task, undo refuses to restore the old content; a merge redo likewise does not move away source-directory children added afterwards.

Closing the task window only hides the interface — the app still owns the tasks; closing the browsing window that started them cancels those tasks and waits for cleanup, and closing a tab does not transfer task context; quitting the app cancels every transfer and waits for the worker threads to stop writing to disk. Atomic renames, Move to Trash / Delete Immediately, and the tool runs behind ZIP Compress / Extract keep using their existing code paths and make no claim to be pausable midway. The status bar keeps its busy indicator; transfer errors appear in the task, while other operations keep their existing error reporting (printed in smoke-test mode rather than shown in a modal).

## 7. Conflict dialog (matches Finder)

macOS exposes no public API for Finder's conflict dialog, so ours is built in-house but behaves as Finder's does: each conflict is asked once — **Keep Both** (the default, non-destructive) / **Skip** (when there are several items) / **Stop** / **Replace** (destructive style) — with an extra **Merge** for folder-onto-folder conflicts (a recursive merge, with child conflicts following the same policy). When several conflicts are involved there is an **"Apply to all (N items)"** checkbox, and ticking it applies the same choice silently to the remaining conflicts. The body text gives both sides' modification times and sizes and says which is newer.

A transfer task's conflicts are presented as an inline choice within the task itself, keeping the choices and the apply-to-all policy above; the inline version allows Skip even for a single item and sets no Return default button that would apply across tasks. Other tasks remain controllable while a decision is pending, Cancel ends the wait and cleans up, and Stop halts the rest of the batch. The task interface's layout and status wording are Tursora's own design and make no claim to be a pixel-for-pixel copy of Finder or KIO; the evidence for Dolphin's task routing is in the [file operation tasks record](research/file-operation-tasks.md).

## 8. Filtering (Finder's form, Dolphin's semantics)

The UI uses a **name filter field on the right of the toolbar** (`NSSearchToolbarItem`, labelled `Filter by Name`, collapsing to a magnifying-glass icon in a narrow window), focused with `⌘F` by default (customisable in Settings). Typing filters the current folder first and the number of matches appears in the bottom status bar; in an ordinary folder, once there is input, the top of the pane shows `Current Folder` and a **Search Options…** entry point. Only opening the options enters a search that includes subfolders and expands the detailed conditions, at which point the same toolbar field switches to editing the name search term; there is no separate toolbar Search button and no second name field. A ZIP keeps local filtering and shows no recursive options. Esc or ⓧ clears the field and exits, returning focus to the list; simply clicking elsewhere does **not** cancel non-empty input. Once collapsed to an icon, the same filter shortcut expands it again, and it collapses on its own if focus leaves while there is no input. The interaction comparison and the design boundaries are in the [search input record](research/search-input-reference.md).
Filter semantics follow Dolphin: a case-insensitive substring, `*` / `?` wildcards, applied to the current pane (including subfolders expanded in place); it is remembered per pane, the search field shows the active pane's filter term, and changing folder clears it.

After navigating from Favorites, Group By / Use Groups in the toolbar and the View menu still act on the active pane even while focus is still in the sidebar.

## 9. Grouping (a 1:1 match with Finder's Use Groups / Group By)

- The **Use Groups** toggle is `⌃⌘0`; the **Group By** submenu (shared by the View menu and the toolbar's Group button) offers None `⌃⌘0` / Name `⌃⌘1` / Kind `⌃⌘2` / Application / Date Last Opened `⌃⌘3` / Date Added `⌃⌘4` / Date Modified `⌃⌘5` / Date Created `⌃⌘6` / Size `⌃⌘7`. Turning grouping off and on again returns to the last key (Kind the first time); grouping and the last field are saved together under §5's folder policy.
- List view: the group header is a full-width, sticky group row that cannot be selected (rubber-band selection included), has no disclosure triangle and is always expanded; items within a group follow the current sort, and folders inside a group can still be expanded in place. Icon view: one section per group, with a sticky group header.
- The grouping rules (`Grouping.swift`, pure functions) take their labels from Finder's own string tables ([research/finder-group-labels.md](research/finder-group-labels.md)): Name uses the first letter, with digits and symbols going to `#` and sorting last; Kind is Finder's category name (Applications / Documents / Folders / Images / Movies / Music / PDF Documents / Presentations / Spreadsheets / Text / Source code / HTML / AppleScript / Fonts / Contacts / Mail Messages / Webpages / Other Documents / Other — there is no Archives, so archives go to Other), and the groups sort by name; Application is the name of the default application, with folders going to Finder; dates are Today / Yesterday / Previous 7 Days / Previous 30 Days / by month within this year / by year further back, newest first, and **future timestamps go to No Date**; Size puts Folders first and the rest in decimal orders of magnitude, "Under 1 KB" / "From 1 KB to 10 KB" / …, largest first.
- Still inferred: the bucket boundaries for Size; the ordering of the Kind groups; using access time for Date Last Opened as an approximation of Spotlight's last-used; what the "Earlier" key is for.

## 10. Info windows (Get Info, matches Finder)

- **Show Preview** `⇧⌘P`: a preview pane docked on the trailing edge of the window, beside the file view. It shows the selected item, or the current folder when nothing is selected, and it stays open as you navigate. A selection of several items shows nothing rather than an arbitrary one of them; inside a ZIP and in search results it is blank, because those have no plain filesystem target to preview. It is one pane per window, like the terminal and the Folders tree, and it is resizable between 220 and 720 pt; its visibility and width are restored with the session. Markdown is rendered as rich text — headings, lists, block quotes, fenced code, inline emphasis and GitHub tables, following the light or dark appearance (D81) — and everything else falls back to Quick Look. Links in a rendered document are shown and selectable but **not followed**: a previewed file is untrusted content, and a relative link resolves to a neighbouring path that could be an application. Images appear as their alt text; nothing referenced by a document is loaded. `⌃⌘P` toggles icon thumbnails, which held ⇧⌘P before the pane took it (D82).
- **Get Info** `⌘I`: one window per selected item (with more than 10 items, a single summary window instead); with nothing selected, the current folder itself. Pressing `⌘I` again on the same item only brings the existing window to the front; Get Info and the summary window compare existing targets by normalised URL, so differences in how a path is written do not produce duplicate windows. **Show Inspector** `⌥⌘I`: a single floating panel that follows the selection in the main window's active pane (showing a summary for a multiple selection). **Get Summary Info** `⌃⌘I`: "Multiple Item Info", with Kind written as "2 documents, 1 folder" and Size the total. The three are the ⌥ / ⌃ alternates of the same menu line.
- The sections and labels come from Finder's `InfoWindow*.nib` ([research/finder-menu-icons.md](research/finder-menu-icons.md)): the header (64 pt icon, name, size, Modified), **General:** (Kind / Size / Where / Created / Modified / Original (symlinks and aliases) / Version + Copyright (applications) / Capacity + Available + Used + Format (volumes), Locked), **More Info:** (from Spotlight: Dimensions / Duration / Codecs / Authors / Page count / Where from / Last opened…), **Name & Extension:** (editable, committed on Return or on losing focus, undoable; Hide extension), **Comments:** (Finder's `com.apple.metadata:kMDItemFinderComment` xattr, saved on losing focus, on closing the window or on quit), **Open with:** (the default application first, the rest by name, Other…; Change All… confirms before changing the whole type), **Preview:** (`QLPreviewView`) and **Sharing & Permissions:** (three rows for owner / group / everyone, with Read & Write / Read only / Write only (Drop Box) / No Access, changing the POSIX bits; a folder's x bit follows read/write while a file's x bit is left alone; items you do not own are read-only). Every section can be collapsed, and the collapsed state is remembered per section.
- Initially only **General** and **Preview** are expanded and the other sections are collapsed, matching the state observed in Finder on this machine. After that, deliberate expanding and collapsing is remembered per section, and Info, Inspector and Summary share the preference under the same name; opening a window never writes the default out as if it were the user's choice. A `true` saved automatically by an older version takes the new baseline, an old `false` is kept, and a new explicit choice always wins; [evidence and the compatibility trade-off](research/info-disclosures.md).
- Size is written as Finder writes it: "6,148 bytes (8 KB on disk)" for a file, "8 KB on disk (6,148 bytes) for 2 items" for a folder, and "Zero bytes" for 0; folders are totalled recursively in the background and refresh as they go. Where is "Macintosh HD ▸ Users ▸ me". Dates are a long date + a short time.
- When an item is deleted its window closes automatically (the Inspector switches to the current selection instead); when an item is renamed — inside this app the rename broadcast carries from/to, and from outside it is found by inode in the parent folder — the window's title follows, and the browsing pane's selection follows the new name too. A change in the parent folder rebuilds the whole window, but **not while a name or a comment is being typed**; the rebuild waits until editing ends. Each section remembers its own URL, so after the Inspector switches target a late sheet or click does not act on the new target. An Info window can become key but **never becomes main**, so the Inspector and the Go menu keep following the browsing window.
- Not in v1: Stationery pad, ACLs, changing owner/group (which needs elevated privileges) and Apply to enclosed items.
- The Info sections fill the window's width, with 16 pt of margin on each side for section titles and content; Preview stretches with the window width and keeps that width after being collapsed and expanded again.

## 11. Directory watching (matches KDirWatch)

Each pane watches its current folder with FSEvents (including subfolders expanded in place), so external changes — from Finder, a terminal, another pane or another window — refresh automatically within about 0.5 s, and the refresh **keeps the selection and the scroll position** (a renamed item follows its new name). After an in-app file operation completes it additionally broadcasts "this folder changed" (optionally carrying the rename's from/to), so other panes and Info windows in the same app refresh immediately without waiting for FSEvents. FSEvents reports real paths (`/private/var/…`), so both sides must resolve symlinks before being compared.

The list's scroll position is saved by the visible top of the content, accounting for the space the system column header occupies; after a refresh at the top, a compress or extract, or an undo or redo, the first row is still fully visible and clickable. When the list gets shorter, the old scroll position is clamped into the valid range.

## 12. Menus and icons (matches Finder)

Menu bar and context menu items carry SF Symbols, with the symbol names taken from Finder's own `MenuBar.nib` (New Folder = `folder.badge.plus`, Get Info = `info.circle`, and so on — see [research/finder-menu-icons.md](research/finder-menu-icons.md)); the few items the nib does not spell out use generic symbols. The menus are built in code, with no nib. Every shortcut is listed in [SHORTCUTS.md](SHORTCUTS.md).

## 13. More actions and Share

The toolbar's More (three dots) menu offers New Folder, Open, Get Info, Quick Look, Rename, Duplicate, Compress, Extract, Copy, Paste and Move to Trash according to the active pane's selection; with an empty selection only the folder-level commands and an available Paste stay enabled, and Rename allows only a single selection. The menu targets the window, which dispatches to the current pane, so focus in Favorites or in the location bar does not interfere. Share is the system `NSSharingServicePickerToolbarItem` and supplies the file URLs of the current selection; it supports list and icon views, multiple selections, split panes and filtering, and is disabled when nothing is selected. The service and the recipient are chosen by the user in the system interface.

**Design boundaries**: no display, reading, editing or grouping of file Tags; no Import from iPhone. Tags already on disk are not removed. The evidence and the trade-offs are in the [More menu comparison](research/finder-actions-menu.md).

## 14. ZIP compression and extraction (follows Finder)

- Compress is offered in the File menu, the More menu and a file's context menu; a single item produces `<original name>.zip` (keeping the original extension) and several items produce `Archive.zip`, saved into the folder currently being browsed.
- ZIP files offer Extract; when ZIP browsing is turned off in Settings, opening or double-clicking a ZIP also extracts it inside the app. For the opening behaviour when it is enabled, see §18; an explicit Extract remains available whenever a ZIP is selected in an ordinary folder. Several selected ZIPs are processed in order. Extraction writes next to the original ZIP: a single root item keeps its own name, while multiple root items go into a folder named after the archive.
- On a name collision ` 2`, ` 3` and so on are appended in turn; existing content is never overwritten or merged, and both the source files and the ZIP are kept. The relevant panes refresh afterwards, and Compress / Extract support undo and redo.
- The slow work runs in the background with the status bar showing busy; a failure reports the error and no half-finished result is published. The system archive tool handles the content in a private temporary directory, keeps the path and symlink escape protections, and preserves resource forks and the download quarantine attribute.
- Only plain ZIP is supported at present; password-protected archives and other formats are not part of this implementation. No system file association is registered.

## 15. Servers and mounted volumes (follows Finder)

- Go → Connect to Server… (`⌘K`) accepts SMB / CIFS, NFS, WebDAV HTTP(S) and the legacy AFP addresses the system still supports. Format errors are shown inline; embedded passwords are not accepted, and macOS's own authentication interface handles the login and the share selection.
- A connection starts only on an explicit submission — Connect, or Return in the address field; the address field losing focus, or clicking Cancel, must not start a new mount request. The verification status of the fix for the focus-loss submission regression is in [this round's on-device record](research/computer-use-2026-09-12-inline-zip.md).
- Mounting is asynchronous through the system's NetFS, and on success the app navigates to the local mount path that was returned; no network filesystem is implemented in-house. Network volumes appear in Locations automatically with a network icon and support Eject / disconnect; removable local volumes keep their existing eject behaviour.
- Closing the connection window cancels the request so a stale callback cannot navigate a window. Whether SMB, WebDAV and the other protocols actually work depends on the system and on the server.
- There is no SSH / SFTP backend, no server discovery, no favourite servers and no reconnection after a drop. This round verified only addresses, state transitions and the volume policy; with no real server address available, no remote read/write testing was carried out.


## 16. Settings and custom shortcuts

- Tursora → Settings… (`⌘,` by default) opens the app-level settings window, split into four panes — General / Shortcuts / Terminal / Updates — with General selected the first time. The General pane holds the general options, Startup, Opening folders, Folder View Settings and Terminal & ZIP; changes take effect immediately and are persisted. Startup's Reopen windows and tabs on launch is on by default; for the semantics, see §22. Folder View Settings chooses between per-folder memory and one shared default, with the semantics in §5; the Updates pane is covered in §20.
- Opening folders offers to make Tursora the application macOS opens folders with — the handler for `public.folder`, which `open .` in a terminal, a folder dropped on the Dock icon and any application that asks the system to open a folder URL all resolve through. It does not capture Finder's own window, nor another application's "Reveal in Finder", which is a Finder-specific call (`NSWorkspace.activateFileViewerSelecting`) and is unaffected by the handler. A line says which application holds the role today ("Folders open in Finder.", "Tursora opens folders.", or "Folders open in another application." when the name cannot be read), and the button below it is disabled once Tursora holds it. Pressing it asks macOS, which shows its own confirmation; declining changes nothing and the line is unchanged. The state is read from LaunchServices each time the pane appears rather than remembered, because the role can be handed to another application elsewhere; the comparison is by bundle identifier, so the same build is recognised from /Applications, a disk image or a build folder. The button reports that it needs a packaged application when run from the bare executable. Nothing is written to LaunchServices' own preferences (D86).
- Shortcuts offers a searchable catalogue of the app's commands, covering both bound and unbound commands in the main menu as well as extra keyboard actions such as Return / Enter to rename, Space for Quick Look, tab cycling and number positioning, the alternate zoom bindings, and cancelling an archive being opened. Recording, Clear, per-item Reset and Reset All Shortcuts are all supported; a cleared command stays unbound, which is distinct from "use the default because there is no override".
- Bindings are persisted globally and the menus and open windows update immediately; an older custom Filter binding is kept, and the default is still `⌘F`. A conflict names the command that already holds the key and keeps the original value; resetting a single item also checks for conflicts, and resetting everything restores a consistent default set. Use Groups defaults to `⌃⌘0`, and Group By → None no longer takes the same key a second time.
- General commands accept Command / Control combinations or function keys; the extra File View actions also accept Return, Tab, Space and Escape combinations. A plain Escape cancels recording, and restoring the Escape default goes through Reset. Known macOS combinations are reserved; recording follows the current keyboard layout and keeps the character as typed, resolving Shift equivalences only when comparing; the US Plus is equivalent to Shift–Equals, and a standalone Plus on another layout is not forced into an Equals.
- File-view commands fire while a file view — the list, the icon grid or a column — has keyboard focus. App commands still go through AppKit menu validation and the responder chain, and copy, paste, undo and the rest in a text field keep their native targets. Control-only combinations and function keys are handed back to the original view while typing in a text field or in SwiftTerm, except for the configured terminal toggle. Native text editing, path completion, directional selection, dialog confirmation, shell/readline keys and mouse gestures are not redefinable commands in this catalogue. Main-menu items and alternate actions are listed separately and configured independently.
- Backspace and Forward Delete are saved, displayed and matched separately, and Fn-Delete is interpreted as a forward delete. Menu matching converts only a copy of the event into AppKit's corresponding menu character; the input events that reach native text fields and the terminal are not rewritten. A disabled command still obeys menu validation and is not executed just because it was rebound.
- Filtering is still a name filter over the current folder; the separate recursive search is in §19. The extension display setting affects only interface labels and changes neither filenames nor Finder's per-file Hide extension flag.
- Terminal panel and Browse ZIP archives are both on by default, while an existing explicit choice to turn one off is kept; with no preference recorded, the new default is used. The terminal toggle only makes the entry point available and does not start a shell by itself. Turning the terminal entry point off hides an existing panel and keeps its session, and the settings text explains that it can be re-enabled and continued.
- The full default bindings, the recordable range and the responder-chain rules are in [SHORTCUTS.md](SHORTCUTS.md); [the settings comparison](research/settings-and-shortcuts.md) still holds the evidence from the original Filter-only stage and does not mean that only one shortcut is supported today.

## 17. Terminal panel

- The toolbar's terminal button and View → Show / Hide Terminal (`F4` by default, customisable) expand and collapse the terminal at the bottom of a browsing window. The button's state, title, tooltip and overflow menu reflect whether the current window has it expanded; the button is disabled when Settings has turned the terminal entry point off. Each window has at most one terminal, shared by all of that window's tabs and split panes; the panel's height is draggable.
- As the user last confirmed, the bottom of the window shows no terminal entry point, icon, job count, animation or timer, and nothing is polled from the process for that purpose. The terminal is operated from the toolbar, the menus or a shortcut; quitting, closing a window or Restart still checks for running jobs at the moment of the action.
- The bottom status bar also drops the free disk space and the query behind it, keeping the item / selection counts, the filter, the search / ZIP context, the zoom and file-operation progress; a narrow pane keeps the counts and the context first, and zoom remains available from the menus and gestures.
- It uses SwiftTerm 1.15.0's native terminal view with a real PTY, and starts the current user's interactive login shell by default; Settings → Terminal offers System Login Shell or Custom Shell. A custom entry is an absolute path to an executable and accepts no extra arguments or command fragments; saving and actually launching are validated separately, and a missing or non-executable path shows an inline error. A shell choice takes effect only for the next new session or restart, and re-showing an existing panel neither applies the new shell nor ends the running process.
- The font can be any installed monospaced face plus System Monospaced, defaulting to the system monospaced face at 12 pt with a range of 8–36 pt; typing a value and pressing Return, or moving focus away (with Tab included), commits and validates it, and the stepper goes through the same persistence. Colours default to Follow Appearance, and can also be fixed to Dark, Light or a Custom six-digit hexadecimal text / background colour; font and colour changes apply immediately to every open terminal without restarting the shell or writing into its input. Restore Terminal Defaults restores the factory values above. A fixed scheme does not follow the system light/dark switch; custom colours define only text and background and make no claim to be a full ANSI palette editor.
- The initial working directory is the active folder at the moment the panel is first opened; when the active pane is inside a ZIP, the folder holding the original ZIP is used, and the shell is never started or restarted inside the temporary copy. The process starts only when the toggle is enabled and the panel is shown for the first time, or on an explicit Start or Restart.
- Browsing navigation, switching the active tab and switching pane all update the terminal's target folder, and Terminal follows the browser folder in Settings → Terminal controls whether that folder is handed to the running shell (on by default). zsh syncs at an empty prompt through a private request file and a ZLE FIFO callback; while it is busy, inside a read, on a continuation line or with an uncommitted command, the input is preserved and the latest request is deferred to a safe prompt, and the sync is likewise preserved while the panel is hidden. bash and fish have no wake-up channel, so a request takes effect only at the next prompt the user draws and nothing happens while they are idle. The path is passed as data — no cd and no line-clearing keystrokes are injected into the PTY, and the user's dotfiles are not modified; with the toggle off the Restart target is still updated and the tooltip explains why.
- zsh, bash and fish all report their own current directory at the prompt (OSC 7, a percent-encoded `file://` URL), so the user does not have to install shell integration themselves: zsh uses a temporary `ZDOTDIR` (restoring the original value before reading the user's `.zshenv`), bash uses a temporary `--rcfile` (reading the user's `/etc/profile`, `~/.bash_profile` / `~/.bash_login` / `~/.profile` / `~/.bashrc` in login order, and appending to rather than overwriting `PROMPT_COMMAND`), and fish uses `--init-command` (evaluated after `config.fish`). Other shells still have only a manual Restart, and the tooltip states the supported range. Every launch argument is a separate argv entry, and the integration file's path never becomes executable text.
- Browser follows the shell folder (on by default) makes the current tab's current pane follow when the shell changes directory on its own, taking the same code path as manual navigation, with the panel never reading or writing the filesystem. It applies only while the panel is visible; a folder equal to the one this panel just requested, equal to the browser's current folder, or identical to the previous report triggers no navigation, so the two directions never pull against each other. Only local folders are reported (the hostname must match this machine or localhost), and remote or malformed URLs are ignored; only the active pane changes, never the other half of a split or another window, and folders missed while the panel was hidden are not reported retroactively.
- The top is a single compact action bar, keeping the Terminal title, the start / restart icons and the hide button; the two permanent Started in / Restart in directory lines are removed. The confirmed folder, a pending sync, errors and the next launch target live in the tooltip and the accessibility description; the launch location is not presented as a live cwd. After the shell exits on its own the output is kept, and Start Terminal begins a new session.
- The toolbar button, F4 and the close button in the panel's title bar only hide the panel; the owning window keeps the original PTY, its output and its jobs, and showing it again uses the same session. Disabling the terminal entry point likewise only hides and keeps it, so re-enabling lets you expand and continue; font and colour changes still update these hidden sessions.
- Only Restart, closing the owning window or quitting the app ends a session. Detection covers the current PTY's foreground, background and stopped jobs; when the state is unknown it asks, conservatively. The confirmation defaults to Cancel; cancelling does not end the shell, does not clear the output and does not start window or app cleanup. Once Restart is accepted, the old session is reclaimed and a new one is created in the current target folder.
- Quitting the app first gathers the sessions of every window (including panels that are hidden or whose entry point is disabled) and asks for confirmation; only once that passes does it set the quitting state, save the logical workspace synchronously, cancel transfers and wait for the PTYs it owns to be reclaimed. Closing a window deals only with its own terminal, and an explicit acceptance does not affect other windows' terminals.
- This round provides neither multiple terminal tabs nor PTY session restore across an app restart. bash and fish have no reply channel, so a failed cd is not reported as a failure the way zsh reports it and is simply retried at a later prompt; a bash session is an interactive, non-login shell. Job detection comes from process state and runs no probe commands; the precise detection boundaries and the verification stage are in the [session lifecycle](research/terminal-session-lifecycle.md), and the scope and limits of two-way sync and of bash / fish support are in the [two-way sync record](research/terminal-shell-sync.md).

The settings implementation and where it differs from the Rascal source are in [terminal customisation](research/terminal-customization.md); collapse-and-keep and the termination confirmation are in the [session lifecycle](research/terminal-session-lifecycle.md). The 0.2.1 folder following, compact action bar and simplified bottom bar replace the earlier presentation, and the integration and verification progress is in [this round's record](research/terminal-navigation-0.2.1.md). The scope, evidence and limits of two-way sync and of bash / fish support are in [this round's record](research/terminal-shell-sync.md).

## 18. ZIP browsing

- The toggle is on by default; Open or a double-click on a ZIP in an ordinary folder enters the ZIP's root in the current pane instead of opening a separate archive window. The archive's original root structure is preserved: a single top-level folder is not silently dropped and no wrapper layer is added.
- It reuses all three file views, in-place expansion, grouping, sorting, zoom and the current-folder name filter; filtering is still not a recursive search. The location bar and the breadcrumbs show the original ZIP path plus the inner folder — for example `/Downloads/Sample.zip/Notes` — and never a temporary path. Typing a ZIP root or a subfolder enters it; typing an ordinary file inside the archive does not trigger an external open.
- Back / Forward, the history menu, tabs and split panes work as they do for ordinary folders. Up moves from an inner folder to its parent; Up at the ZIP root returns to the folder holding the original ZIP and selects the ZIP. Closing the tab or leaving the archive does not clean up its copy, so history can still go back.
- Every folder in an archive is read-only: you cannot create, rename, cut, paste, drop into, delete, Duplicate, compress or extract inner items, or move them to the other pane, and there is no editable Get Info / Inspector. Copy and dragging out only copy; the destination can be an ordinary folder or another writable pane. Quick Look, Share and an explicit Open use a path-validated temporary copy.
- The status bar shows a short `ZIP · Read-only`; the tooltip explains the temporary copy, that external edits are not written back, and Save As. There is no extra scope bar and no Extract All button; to extract, return to an ordinary folder, select the original ZIP and use Extract as described in §14.
- The first open prepares a complete private extracted copy in the background, and panes on the same archive share one session. While preparing, it shows Opening with the filename plus Cancel; Escape and Back also cancel while the file view has focus. Cancelling keeps the previous folder and selection, and when a first restore has no folder yet it falls back to the original ZIP's parent folder. Leaving, or closing the pane, tab or window, cancels that waiter, and the last waiter to cancel stops the underlying process and cleans up the unfinished copy; reopening the tab after closing prepares the original target again. Quitting saves the logical location first and then waits for the preparation process to end and for cleanup. The copy is kept until Tursora quits so that external applications do not lose a file they are using; changes are not written back into the ZIP, so use Save As when the edits need to be kept.
- A failed preparation shows an inline error with Retry and Open Enclosing Folder, keeping the visible original folder and selection; a failed restore at launch still remembers the original logical target, the tab and the window show the name of the requested location, and Reload / ⌘R retries; once the original ZIP is repaired, the inner target can still be opened through the system directory alias. If one member of the temporary copy disappears during enumeration, only that item is skipped, while other read errors are still reported.
- With the ZIP browsing toggle off, existing archive tabs and their history remain safely browsable read-only, while newly opening a ZIP in an ordinary folder falls back to extraction. A plain Open on a ZIP nested inside an archive uses the system default application rather than entering another archive session automatically. Only plain ZIP is supported; password-protected archives, other formats, writing back into an archive, and automatic reloading after the original ZIP changes externally are not part of this implementation. The implementation and verification boundaries are in the [archive browsing research](research/archive-browsing.md).

## 19. Search (Dolphin semantics, macOS backend)

- The **Search Options…** entry that appears after filtering the current folder, View → Search… and `⇧⌘F` all expand the current pane's recursive search conditions, carrying over the toolbar's name input. The options cover content, scope, kind, modification date and saving the conditions; no second click is needed to run a Search. Name and content input runs automatically 500 ms after typing stops, and Return runs it at once; changing kind, date or scope also runs it automatically. No query is started while an input method still has uncommitted composition text. Name search is a literal containment test, and the filter's `*` / `?` are interpreted as wildcards only in current-folder filter mode.
- The scope is Current Folder (including subfolders) or Home (including subfolders), and the concrete root path is shown. The name, content, kind and modification-time conditions combine with AND, and the name is a case-insensitive literal containment test. Dates support presets and custom start and end bounds; the start is inclusive and the end is exclusive, a preset is converted to fixed dates when saved, and reopening shows the actual bounds. Clear empties the conditions, the results and the request while keeping the scope, and starts no broad traversal; only typing again or picking a valid condition runs a search, and a Reload after clearing does not restore the old request. When every condition is empty, the whole tree is not scanned automatically.
- `Using:` picks where a content condition looks. **Spotlight Index** asks macOS and is fast, but sees only what it has indexed — and it cannot tell an unindexed folder from one with no matches, so both come back as zero results. **Scan Files** reads the files itself, so an external drive, a network volume or a folder excluded from indexing is searched too; it skips binary files and anything over 64 MB, reads at most the first 1 MB of each file, and stops after 20,000 files, saying so in the status line each time. The setting is disabled until there is content text, is saved with a saved search, and defaults to the index, so an existing saved search behaves as it did (D85).
- With no content condition, enumeration is recursive in the background, so unindexed folders can still be queried by name, kind and date; packages, ZIPs and symlinks are not recursed into. With `Using: Spotlight Index`, content goes through Spotlight and is limited by the system index, by permissions and by format support; the status text explains the limitation, and zero results do not claim that content was scanned completely.
- The query and any pending input are saved per pane, and running a new query clears the old name filter; a Reload, a completed file operation, an undo and a directory-change refresh all re-run the current search in preference to anything else, keep the real-URL selection for items that still match, and do not leave the search because of a source-folder key check. Cancel cancels both the pending input and the running query, keeps the partial results already gathered and marks them as cancelled; late results from an old query never overwrite a new one. Switching tab or activating the other pane does not cross state — a deferred query still belongs to its original pane and does not steal focus; navigating, or closing the pane, tab or window, cancels the pending input. Back, Close Search and the toolbar's Esc / ⓧ return to the original folder and clear the input.
- Search results are not a folder and not a ZIP logical address. The list's Location column, the icon view's location label and the full-path tooltip show where each item came from; switching mode, filtering, grouping, selection and subsequent file commands all work on the real URLs. Open / Quick Look / Copy / Get Info / Rename / Duplicate / Trash and cross-pane transfers are available; Reveal in Enclosing Folder opens the parent folder in this pane and selects the exact item. There is no default write destination, so the results background does not support Paste / New Folder / Compress / Extract; dropping onto an explicit folder result still uses that folder.
- Save stores the current conditions and scope under a name you type; they are discoverable through the Saved Searches menu, Open and Delete. Deleting removes only the saved conditions, which can still be run again after a restart. The app's save format is not interchangeable with Finder Smart Folders.
- Search is disabled inside a ZIP and the temporary extracted copy is never traversed; an ordinary folder can find the ZIP file itself. Reload re-runs the current request. Permissions, launch failures, cancellation and empty results are all explained with non-modal status text. The implementation evidence and the boundaries are in the [search research](research/search.md).

- At most 50,000 items are shown at once; the recursive walk truncates by matched results, and Spotlight examines at most the first 50,000 indexed candidates; on reaching the limit it says explicitly that the conditions should be narrowed.

When a search batch changes the row order, an already-open context menu stays bound to the real files it was opened on. When a bulk file operation selects both an ordinary folder and descendants along the real directory path, only the topmost folder is processed, once; undoing a Trash restores the whole tree. Copy / Move / Duplicate also normalise the same set of sources when the task is created, and Duplicate copies each retained source into its actual parent folder. A symlink does not subsume an explicitly selected `link/child`: even when only the real folder `root` and `root/link/externalChild` are selected, the link in between makes the latter a separate source. If the selection contains a real folder under a link together with an ordinary child of it, with no link between the two, they are still de-duplicated by parent folder; the operation's targets are never replaced by resolving links.

## 20. Software updates (native Sparkle update flow)

- The officially packaged app checks for, downloads, verifies, installs and relaunches updates through Sparkle 2.9.6. Tursora → Check for Updates… and the identically named button in Settings → Updates share one app-level updater; it is unaffected by tabs, split panes or the current folder, and adds no shortcut.
- Automatically check for updates is on by default and checks on Sparkle's daily cycle; it can be turned off and the choice is remembered. With automatic checking off, manual checks still work; the user's saved preference is not overwritten at every launch, and no extra network query is forced.
- Automatically download and install updates is a separate option, off by default. With it on, downloads can run in the background and a successfully verified update can be installed on quit; Sparkle prompts when authorisation or another user action is needed. Turning automatic checking off disables that control while keeping its existing choice, and re-enabling checking makes it operable again.
- The two options govern subsequent checks and the automatic-update policy; they do not cancel an update already downloaded or already scheduled to install on quit, and Sparkle's existing session semantics are kept. Whether the manual check entry point is available depends on the updater's current state, and a new check cannot be started again while one is being processed in the background.
- Updates shows the time of the last check, or that no check has been made yet; when the updater's configuration fails to start, the reason is shown inline and the corresponding actions are disabled. The unpackaged SPM executable and smoke mode do not construct Sparkle at all, and schedule no update network requests and no update dialogs. Tests use an injected driver to verify the controls and their states.
- Updates follow only GitHub's latest official release; prereleases do not enter the stable channel. The public HTTPS feed is the `appcast.xml` on the latest release, where the DMG points at the fixed asset URL for the corresponding version, and the downloaded content is verified against an Ed25519 signature before the app is extracted and installed. No optional system profile is sent; the app is still ad-hoc signed and not notarised, and the update signature does not change that.
- The updater has shipped since 0.2.0, which also published the first stable feed. The implementation, the signing configuration, the actual release and the verification stage are recorded separately in the [software update research](research/app-updates.md) and the [official release record](research/release-0.2.0.md); finding that you are already on the latest version is not the same as having tested the full install / relaunch path.

## 21. Download and installation

- The README gives the installation steps for the current release and the Homebrew commands directly, after the introduction and before the feature table. The "Install guide" in the website's hero primary button and in its navigation is an in-page `#installation` jump; "Free download" separately points at the real latest stable release. The installation section describes downloading the DMG, opening it, copying to a writable directory of your choice and launching the installed copy, reuses the real transparent installation screenshot, and shows the first-launch command for a trusted download directly. What is offered today is the published 0.2.0 DMG; no non-existent newer asset is linked.
- The project's own Homebrew tap uses this repository's `Casks/tursora.rb` directly. Run, in order, the explicit-URL `brew tap zerolfx/tursora https://github.com/zerolfx/Tursora`, then `brew trust --cask zerolfx/tursora/tursora`, which authorises this cask alone, and finally `brew install --cask zerolfx/tursora/tursora`, continuing only after each step succeeds. The explicit URL in the first command must not be omitted; running install without the tap installed makes Homebrew look for the default `zerolfx/homebrew-tursora`, and a message that that repository does not exist means the explicit tap step should be checked first. The released version and its SHA-256 are pinned; the current cask uses the real `0.2.0` DMG and is marked `auto_updates true`. An Apple membership does not have to be bought first for one's own tap, but the package is still not notarised; the download quarantine is kept and no bypass command is run inside the cask. The acceptance criteria for the official `homebrew/cask` are separate from one's own tap — see [Homebrew evidence and installation verification](research/homebrew.md).
- At the user's explicit request, the main installation flow in the README, on the website and in the maintenance notes is fixed as the three commands tap → single-cask trust → install, and the explicit trust is a required step of the documented flow, not merely a fallback note after an error. Homebrew's full-name install may itself grant the same single-item trust automatically, so it cannot be claimed on that basis that omitting trust fails on every version; trust is not granted for the whole tap, and the global check is not turned off. This documentation revision changes no released app version or build and republishes no binary; the trade-offs are in D58.
- The canonical screenshots in the README, in the research records and on the website must be PNGs of real windows, transparent outside the native rounded corners and anti-aliased at the edges; deterministic processing protects the interior pixels, and the UI must never be generated or retouched. The website build checks the whole image directory, and a white background must not be papered over with CSS — see [this round's screenshot audit](research/screenshot-audit-2026-09-13.md).

- This release and later ones ship `Tursora-<version>-macOS-arm64.dmg` and a SHA-256 checksum file directly, with an update appcast attached to official releases. When the disk image is opened, the window shows Tursora on the left, Applications on the right, and an arrow in between pointing at the destination; dragging the app into Applications completes the installation. Applications is a link to `/Applications` and there is no extra install script; the installation directory is not restricted by that link, so `~/Applications` or another writable location can be chosen instead.
- The image presets a 640 × 280 window and 128 px icons, with the layout written straight into Finder metadata at build time. macOS performs the copy when the user drags the app normally; the file manager's ZIP browsing and ordinary file-operation behaviour are not modified.
- Published tags and assets are unchanged; the current installation flow documents only the official DMG and the Homebrew install, and provides no migration steps from older versions.
- The build is currently ad-hoc signed and not notarised. The README and the website promote running `xattr -dr com.apple.quarantine` against the installed copy's actual path to a directly visible first-launch method; you can also type the command, add a space and drag the installed app in to fill the path. It applies only to a copy whose official origin is confirmed and whose SHA-256 matches that version; it does not clear all extended attributes, does not repair a damaged copy and is no substitute for notarisation. An app the user owns and can write to usually needs no administrator privileges; a read-only DMG, ownership by another account, Homebrew directory permissions and organisational policy are handled separately, without sudo and without modifying system policy. The graphical Open Anyway route is kept as an option where the account allows it. A damaged-file warning means re-downloading and verifying first, and a malware warning is not handled as an ordinary quarantine prompt.
- The top of the README and the website provide installation instructions that can be handed straight to an agent, pointing at `/Tursora/install.md` on GitHub Pages; it is published as plain Markdown, unchanged. The guide picks `/Applications`, `~/Applications` or a location the user names according to the actual permissions, and uses an existing usable Homebrew or the official DMG; the install source and checksum, an app that is already present, and the first launch are each checked separately. When Homebrew itself is not writable it uses the DMG, and it does not assume the brew prefix is writable just because the app's destination is. D59 records the scope, and the document is no substitute for real testing on a genuinely non-administrator account or an organisation-managed device.
- No usable Developer ID signing identity was available for this round and the user confirmed there is no certificate yet, so ad-hoc signing is retained. Once Apple Developer Program eligibility, a Developer ID certificate and notarisation credentials are in place, signing and notarisation will be wired up and verified separately; neither the DMG's appearance nor the Sparkle signature substitutes for Apple's trust. Mac App Store distribution and the sandbox design it would require are evaluated separately.

## 22. Workspace session restore (work continuity)

- Reopen windows and tabs on launch is on by default. A normal launch rebuilds the saved browsing windows along with their tab order, selected tab, custom names, the locations of each tab's one or two panes, the active side and the split ratio; it also restores the active window, the window position and size, the minimised state, the sidebar width and collapsed state, and the Folders tree's visibility, height ratio, hidden-folders option and Home restriction option. When an older session has no tree fields, the tree defaults to hidden. Windows or tabs that were closed explicitly do not come back at the next launch; when there is no browsing window at all, launching opens Home.
- What is saved is the logical location and the conditions of searches that were actually run; the launch navigates again and re-runs the query, and neither search results nor unexecuted drafts are saved. A ZIP uses the logical URL of the original archive plus the inner folder, and that target is preserved while preparation is under way, with the temporary extraction directory never written. When ZIP browsing is off and the real archive can be identified, the archive's parent folder is opened instead; an offline or missing path is not guessed from a `.zip` suffix, and an ordinary folder with the same name is not turned into an archive.
- A folder that does not exist, is not mounted or is not permitted keeps its original path, and the existing asynchronous browsing error explains it inside the pane; it is not silently replaced with Home, and no server is mounted or re-authenticated automatically. Once the volume is reconnected you can Reload or carry on navigating. Windows are constrained to the visible area of the current screens, so removing a display does not leave a restored window off-screen; when a split is temporarily constrained by a narrow window's minimum width, the original ratio is still kept so it can be restored once there is room.
- Filter text, selection, scroll position, Back / Forward history, recently closed tabs, terminal processes, file tasks and undo history are not persisted. Both file views keep reading folder properties as described in §5; the temporary view properties of searches and ZIPs are not merged into the session store. Quitting cancels transfers and waits for cleanup only after §17's terminal job confirmation has passed, and restoring a workspace neither resumes a copy nor runs a terminal command.
- The workspace lives at `~/Library/Application Support/Tursora/WorkspaceSession.json`, separate from the folder-view store. Changes to locations, searches, tabs, splits, the sidebar and window state are coalesced and written 0.4 seconds after the changes stop; once the quit confirmation passes, the state is captured and saved synchronously first, and only then are tasks and temporary archives cleaned up, while cancelling the quit never enters the cleanup state. The file is atomically replaced with private permissions, and nothing is written into the browsed folder. The read protection limits are 16 windows, 32 tabs per window and a 2 MiB file; a save that exceeds a limit reports the failure explicitly and keeps the old file, rather than silently truncating the current workspace. Remote-protocol URLs are not accepted.
- A corrupt, unknown-version or unreadable session file is left exactly as it is and that launch still uses Home; later navigation and quitting do not overwrite it automatically either. Settings → General shows the error inline, and Retry Saving Workspace explicitly retries the save with the current workspace; turning the option off and on again also starts saving the current workspace. An ordinary save failure is likewise reported inline, with no modal dialog.
- Turning the option off cancels any pending save immediately and clears the session file while the current windows keep working; turning it back on saves the current workspace at once. A failed clear shows Retry Clearing Saved Workspace, and the failure must not be recorded as a completed deletion.

This stage's implementation and the three completed rounds of automated, packaged and on-device verification are in the [session restore record](research/workspace-sessions.md). The historical pass counts of existing features do not count as this stage's verification result.

## 23. Command palette (fuzzy search across every command and location)

- View → `Command Palette…` (⇧⌘O by default, customisable or clearable in Settings) opens a floating search panel over the window: a search field on top and a result list below. ⇧⌘P belongs to the preview pane, so it is not reused.
- The list covers three kinds of row: every command in the app (its title, the menu hierarchy it belongs to, and that command's **current** shortcut); each favourite in the sidebar's Favourites (`Go to <name>`); and the folders in the currently active pane's forward and back history (`Recent: <path>`, with home abbreviated to `~`, at most 12 entries in each direction, de-duplicated and excluding the current folder). The palette's own commands do not appear in the list.
- Input is matched as a fuzzy subsequence, ignoring whitespace in the query (`new f` is equivalent to `newf`); results are ordered by score, then by category, then by title. A hit at the start, a hit at a word boundary and consecutive hits each add points, while gaps and a late start subtract, so a prefix hit always ranks above a candidate where the same word appears later. Matched characters are bolded within the row. Matching applies to titles only, not to category names.
- ↑/↓ move with wraparound, Return executes, Esc closes; clicking a row is the same as Return. Closing returns focus to the file view.
- Commands that are not currently available are **still listed but greyed out** (with their category and shortcut still shown), and Return refuses to execute them while the palette stays open. Availability is snapshotted the moment the palette opens and re-validated before execution, so a command that has since become invalid is never executed.
- Commands execute with the existing semantics of their menu item (exactly as picking it from the menu bar), and the commands in the catalogue that have no menu item (Rename, Quick Look, Cancel Opening Archive, the next / previous tab aliases, the Zoom In alias, Select Tab 1–9) execute along the same path as their shortcut. A folder row navigates the **currently active pane**; in a split view only the active side is affected.
- The macOS menu-item search built into the Help menu is unchanged; the command palette additionally covers commands with no menu item, favourites and history folders, and executes them directly.

The implementation, the Finder evidence, the inferred parts and the verification stage are in the [command palette record](research/command-palette.md).

## 24. Trash (browsing, Put Back, Empty)

- The sidebar's Locations section ends with a fixed `Trash` entry (SF Symbol `trash`, which cannot be removed or reordered), and the Go menu gains `Trash`. Entering the Trash is just an ordinary directory listing: both file views, multiple tabs, split panes, filtering and grouping all work as usual, and the status bar shows the context `Trash`, in the same form as a ZIP's `ZIP · Read-only`.
- Only the **user Trash** is handled (`FileManager`'s `.trashDirectory` + `.userDomainMask`). Volume-level trashes (`/Volumes/X/.Trashes/501`) have a resolver function but are not browsed, put back or emptied, and the sidebar has only the one entry.
- Inside the Trash, New Folder, Paste, Rename, Duplicate, Compress, Extract, Cut and Move to Trash are disabled (guards sit on both menu validation and the command entry points, and the keyboard path is refused too); click-to-rename inside the views does not start either. Copy, Copy Path, Quick Look, Get Info, Delete Immediately…, Put Back and Empty Trash… are available. Dragging an item out of the Trash follows the existing same-volume move rule.
- **Put Back**: macOS writes Finder's put-back paths into private records inside the Trash's `.DS_Store`, in an undocumented format, and Tursora **does not parse it** — it keeps its own log instead. The `(original, trashed)` pairs returned by `FileOperations.trash` are written to `~/Library/Application Support/Tursora/TrashOrigins.json` (a serial queue plus an atomic write; the original file is kept when a read fails, the format does not match, or the version is not 1). Entries are removed on a successful put back, on emptying the Trash, and when listing the Trash finds the file no longer exists, up to a cap of 5000 entries.
- Put Back is available only when there is a log entry, the original parent folder still exists, and the original path is not occupied; it moves through `FileOperations.moveItem`, registers undo and posts `DirectoryChanges`. When those conditions are not met, the row is greyed out and a tooltip gives the reason (unknown origin / the original folder is gone / the original name is taken), and the origin is never guessed. Undo moves the item back to its **original path inside the Trash** and restores the log entry; redo applies it again.
- **Empty Trash**: File ▸ `Empty Trash…` and the Trash background's context menu. This item has **no shortcut by default**: testing shows that NSMenu ignores Shift for `⌫`-class keys, so a menu item bound to ⇧⌘⌫ also responds to a plain ⌘⌫ and vice versa, and Move to Trash sits earlier in the menu — which means Finder's ⇧⌘⌫ can neither reach this item nor stop ⌘⌫ from triggering an irreversible empty once the user clears the Move to Trash binding. One can be assigned in Settings ▸ Shortcuts when needed. The confirmation dialog uses Finder's wording; a headless run only prints and decides through the injected hook. After confirmation, every top-level item in the user Trash is deleted one by one with `FileManager.removeItem` on a background queue, failures are reported through `FileOperations.report`, and `DirectoryChanges` is posted afterwards. As in Finder, this **cannot be undone**. The menu item is greyed out when the Trash is empty.
- **A refused directory listing** (`~/.Trash` is refused without Full Disk Access) shows a banner inside the pane offering "Open Privacy Settings" and "Try Again", while the existing listing stays usable. **No modal is ever shown, under any circumstances**; a headless run only prints. The condition is `EPERM` / `EACCES` or `NSFileReadNoPermissionError` (including when wrapped via `NSUnderlyingErrorKey`); `ENOENT` does not count.

The evidence, the inferred parts, the boundaries and the verification are in the [Trash record](research/trash.md).
