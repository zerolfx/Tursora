# Application-wide shortcut settings (2026-09-13)

This round extended the recorder, which previously could only change Filter, into a complete catalogue of application commands. This record describes the implementation boundaries and the dedicated evidence; for this stage's final combined smoke run and the scope covered on a real machine see the [customization integration record](customization-integration.md).

## Command catalogue and persistence

`MainMenu.shortcutDefinitions()` generates the catalogue from side-effect-free menu declarations; the same selector is told apart for grouping / sorting by representedObject, and Edit Location / Go to Folder by dedicated suffixes. A dynamic title still keeps the stable ID it started with, so Split View becoming Close Right Pane, or Close Tab becoming Close Window, does not lose the binding. Every menu command is editable, including Compress, Extract, software update and others that have no default key assigned yet.

An additional catalogue covers rename on Return / Enter, Quick Look on Space, cancelling ZIP preparation, Control-Tab / Control-Shift-Tab, Command-Equals and nine tab positions. Each alternative key is displayed on its own and does not quietly disappear when the main menu binding is cleared. The old arrangement in which Use Groups and Group By None were both Control-Command-0 was ambiguous; the former is now kept, and None has no default binding but can still be assigned by hand.

`ShortcutStore` saves overrides as the JSON Data of `keyboardShortcutOverrides.v1`; a missing entry means the default, and an explicitly empty entry means the user cleared it. The old Filter key / modifier is read only when the new map has no entry for it. Unknown IDs are ignored and preserved on later saves; corrupt data / a wrong format / a conflicting override falls back to the safe default, and reading does not overwrite the original data. Both an edit and a single-item reset check for conflicts against the current catalogue and the dynamic system menus; taking over a key that is already in use requires changing the original command first. Reset All restores the complete default set atomically.

## UI and routing

Settings is divided into General, Shortcuts, Terminal and Updates. Shortcuts supports searching by command / category, single-row recording, Clear, Reset and Reset All, with errors shown on the page itself. While recording, keys are intercepted before menu dispatch, so Quit and the like only become candidate shortcuts and are not executed; Escape cancels the recording. Recording ends when settings are closed, when focus is lost, and when the command being recorded is switched.

Menus still go through AppKit validation and the responder chain; they were not changed to forced targets, so that file operations do not intercept text editing. `ShortcutDispatcher` handles the former window monitor aliases and the file view shortcuts, and both views read the same map. In text fields, the Info / Settings field editors and SwiftTerm, Control-only and function keys are left to the current input; the terminal toggle is the exception, so that it can still be collapsed from inside the shell. Command combinations are still dispatched by the native menus; the file view alternatives take effect only when a file view actually has focus. Arrow selection, path completion, Return / Escape in dialogs, the editing controls of shell/readline and mouse gestures are still owned by the native controls and are not part of the application command map.

Menus update live, and the Group By toolbar menu uses the same settings. The three Get Info items keep using alternates only while AppKit's same-key / modifier-containment relation holds; when customised to an incompatible combination they are shown as separate rows, so that binding one does not cost it a visible entry point. Characters such as Plus are saved as they are and are not hard-coded to the US layout. `ShortcutKeyboardLayout` reads the current input source's Shift character mapping from `NSEvent.characters(byApplyingModifiers:)`, resolves equivalent combinations only when comparing conflicts / events, and updates when the input source changes. On a US layout Plus is equivalent to Shift-Equals, while a German layout's dedicated Plus is not rewritten to Equals; on a French layout the digits that need Shift can still trigger tab positions. The basis is this machine's AppKit `NSEvent.h` description of retranslation against the current input source, together with the [Apple menu shortcut documentation](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/MenuList/Articles/SettingMenuKeyEquiv.html). Injected-layout regressions cover US / German / French without changing the user's input method.

## What verification was added

`ShortcutSmokeTests` covers Clear / rebind / Reset per command, unique IDs / conflict-free defaults, rebuilding persistence, migration of the old Filter, retention of a corrupt map, conflict errors, search and recording layout, plus a real NSMenu.performKeyEquivalent, two tabs / two panes, custom events in the list / icon views, old bindings ceasing to fire, Info alternates, and input protection in ordinary text and in SwiftTerm. The existing Settings / Updates smoke tests were updated to follow the new layout and the range of valid keys.

The main task has completed the checks of the real Settings layout and of recording: the Cmd-T conflict was rejected, and after rebinding to Control-Command-T the terminal could be collapsed; F6 can be recorded and opens / collapses both from the file area and inside the terminal. The real screenshot of Show Terminal selected after filtering on `Show` has been through transparency processing, and the selected row, the recorded value and the buttons agree. With the final 95 Swift sources, which include the Plus, delete key and menu alternate regressions, the 3,194-check combined smoke run passed three rounds in a row (`smoke-7` / `8` / `9`), all exit 0, with empty stderr and unchanged sources; the delivery app / DMG checks passed, and the exact results are in the [customization integration record](customization-integration.md).

## Recording function keys and the initial selection

Checking the real settings page found that recording F6 was rejected as empty input: for some function keys the layout retranslation yields an empty string, and the old `??` only handled nil; the characters passed in can themselves be empty. Symbolic constants are now used for the virtual keys that HIToolbox's `Events.h` explicitly marks as layout-independent (F1–F20, arrows, page keys and so on); the other keys still use the current layout, and an empty retranslation falls back to the reported characters. The regression sends `keyCode=97`, empty characters and the Function flag straight to the recorder instead of only calling the recorder's string interface.

When the Shortcuts page opens it scrolls the selected command into the viewport and keeps the search state; previously the logic selected Filter while the list still sat at the top on About. A check of the row's actual visible area was added and passed with the final three rounds. The findings on a real machine above came from root, and the real Show Terminal selection and F6 recording screens after the fix have been checked.

## Menu characters for Backspace and Forward Delete

AppKit's event characters and menu characters cannot be used interchangeably: a physical Backspace usually reports U+007F while the menu uses U+0008; Forward Delete reports U+F728 while the menu uses U+007F. A windowless AppKit probe on 2026-09-13 confirmed that `NSMenu.performKeyEquivalent` and `NSApplication.sendEvent` match on characters and do not convert automatically from the hardware key code or from the Function or Numeric Pad modifiers. The main menu now uses `ShortcutMenu`, which copies and normalises delete events for menu matching only; when nothing handles them, the responder still receives the original event. Even when Fn-Delete reports Backspace's hardware code, the forward-delete semantics of U+F728 take precedence.

The same probe references the production helper and the menu subclass, and verified that a plain Forward Delete, Fn-Delete, Backspace not triggering Forward Delete by mistake, dispatch through NSApplication, and a disabled item not executing all pass; AppKit still returns handled=true for a disabled item that matches, so the regression checks that the command did not execute rather than assuming a false return. The combined smoke run added these behaviours and input protection for Control-Forward Delete in text; this stage's final results are in the [customization integration record](customization-integration.md).
