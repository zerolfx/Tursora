# Text file icon thumbnails (2026-09-12)

What the user pointed at is the text inside the file icon, not Quick Look or the Preview in Get Info. Until now every type used the system Quick Look thumbnail; a page of text shrinks to the point where the writing is hard to make out, and on failure the type icon is kept instead. This round adds dedicated rendering of the opening fragment for plain text, while other types keep using the existing backend.

## Finder and Dolphin evidence

`Icon size`, `Text size`, `Show icon preview` and the `iconViewShowIconPreview` binding can be extracted from Finder's `ViewOptionsWindow.nib`; Text size here refers to the file name label and does not imply that the font size of the icon content can be adjusted separately. This round looked at the same `Feedback.md` in Finder on this machine and observed tiny text on white paper; the exact point size of the paper was not measured, and there is no proof that Finder's private thumbnail implementation uses the same request parameters as Tursora.

Dolphin's preview request comes from `src/kitemviews/kfileitemmodelrolesupdater.cpp:977–1044` in the locally pinned source `5e457ee9e88aa6277fbf056cd5c32462c5318866`, which requests a standard preview and handles the screen scale factor. The text generator actually belongs to KIO Extras: [pinned textcreator.cpp](https://github.com/KDE/kio-extras/blob/6ddac4968aad8ca39862b0420bcc529cc480fe60/thumbnail/textcreator.cpp). It draws the text at the start of the file on paper of roughly 3:4, computes a monospace font size from the available height and clamps it to 7–10 logical pixels, and clips the text that overflows; some builds can syntax-highlight. Tursora borrows its way of keeping the font size and showing a fragment, implements it with CoreText, and does not claim to reproduce KDE's fonts, pixels or highlighting exactly.

The `.thumbnail` in a Quick Look request is a content thumbnail, not a general icon; `iconMode` affects icon decoration and cannot be treated as a switch that raises the text's font size. This round did not use that switch to explain or fix the legibility problem.

## Current behaviour and limits

- Among ordinary readable files, those whose UTType is plainText, sourceCode, JSON or XML, or whose extension is Markdown, YAML, TOML, INI or log, take the text rendering path first. Rich text, other types and unsupported encodings keep going through Quick Look.
- The model layer opens the file in the background without blocking, confirms through the file descriptor that it is a regular file, and reads at most 64 KiB; it strictly decodes UTF-8, or UTF-16 LE / BE with a BOM, and repairs an incomplete final character only when the file really was truncated. Binary control characters are rejected, and empty content falls back to the original backend. The view never reads files.
- At most 8,192 characters are laid out, on light 3:4 paper with dark text and a 7–10 pt Menlo / CoreText font fallback. The paper is document content and stays light even in a dark theme. Real pixels are produced for the target screen scale factor; there is no syntax highlighting.
- The list and icon views keep the original preview threshold of ≥32 pt. Small icons mainly help recognise the content; to read more text, zoom in or open Quick Look. Zooming shows more text rather than squeezing a whole long document onto one page.
- The cache distinguishes path, point size, screen scale factor, modification time and file size. Reloading, zooming, turning previews off and cell reuse all invalidate older requests; when the window's screen scale factor changes, both views request the preview again at the current factor and reject late callbacks for the old factor. A factor change while previews are off starts no request. ZIP content revalidates the readable mapping both when read and when delivered.

## Verification status

In the screenshot stage of this round, before the Dock and the later input-method adjustments, the combined source smoke suite **passed three rounds in a row, 2,024 checks each**, all three exit 0 with empty stderr; that is the total of the combined suite including the text thumbnail regressions. For the final result of the later Dock / input-method stage, see the [Dock research record](dock-menu.md).

`TextThumbnailSmokeTests.swift` covers UTF-8 / UTF-16, CJK and surrogate pairs, read truncation and invalid encodings, the 64 KiB read / 8,192 character layout limits, whitespace and binary content falling back, FIFOs / non-regular files being refused, and symlinks to regular files. The rendering checks verify that real text produces different pixels and check the logical size and the 1× / 2× raster sizes; a fixed font pixel image is not used as a cross-system golden sample.

The callback tests of both real views cover zooming, turning previews off, cell reuse and screen scale factor changes: a new request can be delivered, while a callback for an old size or an old factor cannot override it; a factor update after being attached to a window triggers a reload, the same factor does not reload twice, and no request is sent while previews are off. The provider integration checks include asynchronous coalescing, delivery on the main thread and cache hits.

The release build of that screenshot stage passed, with its log at `/private/tmp/tursora-tabs-appearance-verification/release-final.log`; the root task confirmed that strict codesign, the Info.plist lint and the in-bundle icon consistency check passed. The packaged app really did display the opening fragments of `Brief.md` and `Components.swift`, under the system dark appearance and under a light appearance limited to that process, and turning previews off / on again was checked. The icon zoom slider was moved from step 2 to step 4; by `ZoomLevel.iconSizes` that corresponds to nominal icon sizes of 64→96 pt, not 128 pt, and it is not a pixel measurement of the paper's real size. See the [text fragment icons](../images/features/text-preview.png), the [dark split panes](../images/features/split-panes.png) and the [light split panes](../images/features/split-panes-light.png).

`Palette.css` in the same group still showed the Firefox type icon at the step that was tested, so it cannot be claimed on this basis that every source code format now shows a text thumbnail. Moving between real multiple displays was not tested, and scale factor changes still rest only on the automated raster and lifecycle evidence above. The native checks above come from the release bundle of the 2,024-check stage; the final source verification after the later Dock / input-method adjustments is recorded separately; the transparent-corner handling of the images did not change anything inside the window.
