## Tursora's design boundaries

This round adopts **per-directory memory** by default; the settings and the View menu provide explicit entry points for choosing the strategy. **Shared defaults** use the default values that have already been saved; switching strategy does not quietly promote the active pane into the defaults. The user sets the defaults deliberately, through a separate **Use Current Settings as Default** action. This differs from Dolphin's implementation, which copies the current style when switching to the shared strategy; the aim is to make the strategy choice and a change of the defaults each predictable on their own.

What is saved is the mode, the sort field and direction, the separate zoom steps for list and icons, grouping, and the hidden-files and preview switches; the grouping key that Use Groups last used is saved as well. foldersFirst keeps its existing fixed policy and no persistence is added for it. The filter text, the selection, the scroll position and the history stay as the pane's state for the session, and do not enter the directory record. This is not session restore: a restart only restores the display properties when a directory is visited, it does not rebuild the previous windows and tabs.

Under the per-directory strategy an ordinary modification immediately updates that directory's saved values, but it does not make another open pane showing the same directory suddenly change style. The other pane reads the latest values when it enters the directory again; if two panes are each modified deliberately, the complete set of properties from the last explicit modification is what is saved. The defaults, switching the strategy and restoring the defaults are explicit global / directory operations, and they do make the affected open panes recompute the properties that apply; under the shared strategy an ordinary modification updates the shared defaults and also synchronises the panes that use those shared defaults. Restoring properties must not itself go back through the save path for user modifications, which avoids recursive notifications, overwriting the defaults, or navigating to another directory.

The persistence store lives inside Tursora's own Application Support, uses a versioned structure, takes effect in memory first, coalesces consecutive writes and saves by atomic replacement. The defaults and the directory records are kept apart; with no record the defaults are used, and restoring the current directory deletes its customised record so that it follows the defaults from then on. A corrupted or unrecognised version falls back to usable defaults without raising a modal that would hang the headless test; a persistence failure must not block the view operation of the moment. The exact versions, the migration rules, how errors are presented and the final checks are governed by the implementation documents and the smoke results — this design description must not be taken as a record of verification that has been run.

| Identity or location | Tursora's policy and its cost |
|---|---|
| Ordinary local directory | The key is the canonicalised local path string: it collapses differences in how a path is written, ignores a trailing directory slash, and resolves symbolic links; the query and fragment are not part of the identity and are stripped when the key is formed. Non-file URLs, non-local hosts and pages already marked as virtual are rejected. Computing the key does not require the path to be reachable at that moment, so a temporarily offline location can still use its existing style, and the FileProvider test seam is preserved; actually listing the directory and handling errors remain the navigation layer's job. |
| Path case | Everything is not forced to lower case; the spelling that Foundation's normalisation produces is kept. There is therefore no promise to merge every equivalent spelling on a case-insensitive volume into one record, which avoids wrongly merging two directories on a case-sensitive volume. |
| Symbolic link / Finder alias | A symlink shares the canonicalised key with its target, and a pane pins this navigation's key when it accepts the navigation, so that later edits do not resolve the link over and over and mistakenly write to a new target; when a refresh finds that the link now points somewhere else, the pane reloads. The model does not resolve Finder alias bookmarks, and it does not conflate aliases with symlinks: only a target directory URL that the caller has already resolved and entered shares the target's record. This feature does not extend the existing open / navigate behaviour for alias files. |
| Rename, move, replace | No inode, bookmark or file ID is used for tracking. After a path changes, the existing record for the new path is read; with no record the defaults are used. The old record is kept, so that a new directory appearing later at the original path can inherit it. In-app and external moves follow the same rule, which does not imply that "properties travel with the folder". |
| Mounted volumes | After a NetFS mount it is handled by the local mount path, with no need to write properties to the remote end. The same volume mounted at a different mount point does not follow, and another volume reusing the same path may inherit the record. No remote identity lookup that would block browsing is added, and there is no promise to match automatically by volume UUID. |
| Logical pages such as ZIP and search | Not persisted: the defaults are used on entry and changes made there only stay in that pane for the session; they never overwrite the defaults or an ordinary directory's record. Returning to an ordinary directory re-reads its configuration. The archive check happens before the path key is computed, so a ZIP logical address cannot be mistaken for a disk directory, and still less can an extraction temporary path be stored; the existing read-only operation restrictions stay in place. |

An Application Support path key avoids polluting the user's directories and needs no write permission on the directory; unlike an extended attribute it cannot travel naturally with the volume, and it will not be copied along with a folder onto another machine. Inodes were not adopted because they have to be combined with a volume identity, may be reused and change when something moves across volumes, and because network volume information can be slow or unstable; bookmarks were not adopted because they add complexity around restoration and security-scoped lifetimes. A path string also exposes directory names inside a private store; that store is kept only within the app's own user data area, and is neither published nor written into the project folder.

## Verification principles

The model is verified with an independent store and temporary directories, covering a round trip between two directories, the no-record default, rebuilding the store to simulate a restart, reset, switching the strategy, old-version / corrupted data and path edge cases; the UI is verified for the multi-pane rules in the same directory, all properties in both modes, filter / selection isolation, and synchronisation of the active toolbar and slider. On a fast A → B navigation, only the result of the current navigation may apply properties — a late result for A must not overwrite B. The archive verification checks both that there is no temporary-path record and that the read-only actions are still disabled. The final smoke count, the three-round logs, strict codesign and the packaged-app computer-use evidence are in the [directory view verification record](computer-use-2026-09-12-directory-views.md); reading the upstream source does not mean those checks have passed.

## Independent adversarial review and re-check of the fixes

On 2026-09-12 an agent that had not written the implementation independently read the storage, the pane restore, navigation, list sorting, the tab / split construction and the exit paths, concentrating on whether configuration could be written to the wrong directory, on late callbacks, notification recursion, temporary state leaking into a new target, and save failures. The three problems below were found, and the revised source was then re-checked item by item; this is code evidence, not a run result.

| Finding | Fix confirmed on re-check |
|---|---|
| Every edit resolved the current symlink: when the link was repointed from A to B while the pane still showed A, A's configuration could be written to B. | `BrowserViewController.viewPropertiesKey` was changed into a stored property; `load(_:)` pins the target key when it accepts the navigation, and `BrowserViewProperties.persistViewProperties()` uses only that key. When `reload()` / `refreshPreservingSelection()` find the target key has changed, they re-enter first and restore the new configuration. |
| After the target changed the URL literal stayed the same, so the original check kept A's filter term, its same-name selection and its pending renames. | `load(_:)` now compares the URL and the directory key together; a retarget clears the current history entry's selection / scroll record and the pending selection, a directory change clears the pending renames, and the existing filter-clearing path is used. |
| Background errors from the coalesced save were swallowed, and the interface could not explain why the settings were lost after a restart. | `DirectoryViewPropertiesStore.writeIfNeeded()` keeps the error and the dirty data and delivers `writeStatus` asynchronously to the main queue; a successful retry clears the error and notifies. Settings shows the failure explanation that is still available in this session, together with Retry Saving View Settings. The pane explicitly ignores save status notifications, so that an error message cannot trigger a property restore; the main thread is not notified synchronously from inside the store's serial queue, which avoids a deadlock with the `queue.sync` in `flush()` / when reading properties. |

An exploratory symlink directory-listing assertion failed during the re-check; pinning the directory key and fixing the directory enumeration are two separate problems, and the failing runs were not counted towards the final three consecutive rounds.

An exploratory run confirmed that Foundation returns ENOTDIR when a symlink root directory is enumerated directly. `LocalFileProvider` has been changed to resolve the target before enumerating and to keep the child URLs under the requested path; correct restoration of the property key, and clearing the temporary state after a link is repointed, are covered by dedicated smoke checks. The final three rounds and the hands-on results are in the [verification record for this feature](computer-use-2026-09-12-directory-views.md).

Hands-on use additionally found that when a narrow pane was restored from the Kind icon view to a unified list, the old group expansion during the transition scrolled horizontally and made the Name column invisible. An independent source review confirmed that the original restore only handled the vertical offset. The final restore sets the model first, then mounts the view, and after layout restores that pane's existing horizontal list position; the new assertions check both the name column at the default x=0 and that a deliberate horizontal offset x>0 is not zeroed. This does not write the scroll position into the directory record.
