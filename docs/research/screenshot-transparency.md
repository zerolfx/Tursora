## GitHub Capabilities: Evidence and Limits

- GitHub's official documentation confirms that `.md` can embed repository images, recommends relative paths, and gives a PNG example; images in a private repository are still subject to read permission. It also explicitly supports `<picture>`. [Images and relative paths](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#images)
- GitHub's Primer source sets `background-color: transparent` on `img` inside Markdown tables; the general image rule constrains the maximum width and does not force a white background. Table rows still have a background colour that changes with the theme, so transparent pixels show the background of the row they sit in. [Table rules](https://github.com/primer/css/blob/main/src/markdown/tables.scss#L39), [image rules](https://github.com/primer/css/blob/main/src/markdown/images.scss#L5)
- The official blog demonstrates the `<picture>` pattern for choosing an image by light or dark theme. That capability is available, but this round's README does not implement switching screenshots automatically with the web page theme. [GitHub's own example](https://github.blog/developer-skills/github/how-to-make-your-images-in-markdown-on-github-adjust-for-dark-mode-and-light-mode/)

This evidence supports using transparent PNGs; it does not allow the claim that this repository's online rendering has been checked, and it is no guarantee about future GitHub CSS. This round only consulted the public material above and checked the README preview locally; it did not visit or publish the actual private GitHub README page.

## Processing Rules

The tool is [`app/tools/prepare-screenshots.swift`](../../app/tools/prepare-screenshots.swift), built on the system Swift, ImageIO, CoreGraphics and CoreText, with no extra image-processing dependency. For the exact commands see the [screenshot maintenance workflow](../images/README.md#capture-and-preparation-workflow).

Automatic mode only accepts screenshots that have a near-white outer background in all four corners and where a stable dark window edge can be found. Inside bounded corner regions it identifies the background by a connected fill from the outer corner, then handles the narrow band next to the edge and the anti-aliasing tail out to the measured outer boundary. It does not fit a rounded rectangle, clip to a uniform radius, scale, or rearrange the window content. Edges estimate coverage from the white-background blending relation `C = αF + (1 − α)M` and remove the mixed-in white, so that changing alpha alone does not leave a white halo; when the estimate cannot be made reliably, it refuses to produce output.

`--mask-from` is for callers who have already confirmed that the screenshots are registered: window bounds, cropping, pixel dimensions and scale factor must all match. Only after the root task visually confirmed the same 1200×720 window was the corner alpha of the already prepared dark image applied to the light one. The script only checks dimensions and the restricted corner regions; it does not prove registration or adjust position for you, and interior pixels whose alpha is 255 in the reference are taken entirely from the input image. Another window of the same dimensions must not be used as geometric evidence.

PNGs that match the input format and whose four outermost corner pixels all have alpha 0 are copied byte for byte, without re-encoding. Other inputs are decoded again from the staged PNG file and all protected RGBA is checked pixel by pixel; anything that does not match is rejected. The output, the original and the comparison image may not share a location, and no existing file is overwritten. The path check resolves parent-directory symlinks first, so a file name that does not exist yet cannot bypass the alias comparison; the main image and the comparison image are each written to a unique temporary file first, then moved to the target location without overwriting.

"Interior pixels preserved" means identical to **the RGBA that macOS ImageIO decodes from the source screenshot**, including the re-check after PNG encoding. JPEG already carries compression and white-background compositing loss, so this cannot claim to recover the original uncompressed screenshot or the exact original alpha; different JPEG decoders may also differ by about one level per channel. Keeping the source colour space and not resampling does not remove those pre-existing losses. The `changedPixels`, corner-region extents, transparent / semi-transparent counts, `protectedRGBABytes` and `protectedBytesEqual` in the statistics are there to check the actual scope of the processing.

## Site and README Display Checks

The site still has the three workflows path, split panes and ZIP, with 4 canonical assets in total; the build copies the image bytes as they are and performs no transparency processing. Screenshot links, images and lightbox images use a transparent background, and the container clips the overflow while keeping the displayed rounded corners; the lightbox title is its own block so that a white outer frame does not fill the corners of the screenshot. This CSS only affects presentation, does not modify the interior pixels of the PNGs, and does not mean the product page itself gained a dark theme.

The static build passed at the PNG refresh stage, with 4 assets, 33 local references and about 1,559 KiB in total. The root task checked the desktop image lightbox and the focus restored after closing it in a local browser, with no horizontal page overflow at a width of 390 px; in a 1000 px viewport the local README loaded both tables and all 15 feature images present at the time, and the transparent corners displayed correctly on light and dark backgrounds. The standalone preview row was then removed at the user's request, leaving 14 feature images in the final table; the count and the references were re-checked statically, and the earlier browser check is not being presented as a re-test of the new layout. The site is not deployed and the actual GitHub page has not been verified. The earlier checks without JavaScript, of the selector under keyboard control and in other browsers stand as records of their own historical stages and do not count as fully re-run in this round.
