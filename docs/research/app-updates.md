## Interaction and preferences

Settings currently has four pages — General / Shortcuts / Terminal / Updates — and opens on General. Updates offers the daily automatic check, automatic download and install, a manual check and the time of the last check. The Tursora menu also offers Check for Updates…, which has no shortcut by default and can be given one under Shortcuts.

The automatic check is on by default and can be turned off; automatic download and install is off by default. Both preferences are left to Sparkle to store, and launching the app does not overwrite an existing choice. While the automatic check is off, the automatic download and install control is disabled; Sparkle's effective getter may report it as off, but the saved choice is kept and comes back once checking is turned on again. The manual check stays available, and while the updater is busy in the background `canCheckForUpdates` disables the duplicate entry point.

With automatic download on, an update that verifies successfully can be installed on quit; where authorization or further action is needed, Sparkle prompts for it. Turning the option off neither destroys an existing update session nor cancels an update that has already been downloaded or scheduled to install on quit. This is how the Sparkle lifecycle is used today, and nothing beyond it is promised — no immediate abort of a download and no deletion of its staged files.

## Code and packaging boundaries

- SPM pins Sparkle **2.9.6**; `AppUpdater` wraps one `SPUStandardUpdaterController` and starts it, reads it and changes its settings on the main thread; KVO is turned into an application notification that refreshes the interface.
- `AppUpdateDriver` is the injection boundary for tests. The shared factory used by the smoke test and by the bare SPM executable does not construct Sparkle, and starts no network check, no permission prompt and no install service. A configuration failure is shown inline and disables the actions; a successful retry restores them.
- The initial values live in Info.plist: `SUEnableAutomaticChecks=true`, `SUAutomaticallyUpdate=false`, `SUSendProfileInfo=false`, `SUVerifyUpdateBeforeExtraction=true`; `SUAllowsAutomaticUpdates` is not set, so the checking state decides whether automatic download is eligible. The check interval uses Sparkle's default of 86,400 seconds.
- Packaging puts the complete Sparkle framework into `Contents/Frameworks` with `ditto`, preserving the helper / XPC signatures, the symlinks and the executable permissions. The executable uses the rpath of the framework inside the bundle, with the SPM development directory paths cleaned out; only the outer app is ad-hoc signed, and `--deep` is not used to re-sign the nested helpers.
- Updating belongs to the application lifecycle and does not go through the file browser's undo channel for user files; on quit the terminal task confirmation runs first, and only once it passes do the final save and the file-transfer / PTY cleanup begin. The data model of user file operations, panes and tabs is unchanged. Combined verification with a real Sparkle install / restart has to be recorded separately; the old loopback update result is no basis for inferring that the new confirmation has been tested.

## Release and chain of trust

The stable feed is fixed at `https://github.com/zerolfx/Tursora/releases/latest/download/appcast.xml`. Every stable release carries a single-item appcast containing the embedded release notes, the pinned-version DMG address, the file size, the macOS 14 and arm64 requirements, and the Ed25519 signature of the DMG. There is no delta and no prerelease channel. The feed XML itself is not signed and `SURequireSignedFeed` is not enabled; HTTPS carries the metadata, and the public key inside the app verifies the image that is to be installed. The SHA-256 file is for checking a download and does not replace the signature.

`make-appcast.sh` hands the private key to the official generation tool over stdin, validates the metadata, and then checks the archive signature with the Sparkle tool. The private key is never written into the working tree, never passed as a command-line argument and never printed to a log. The public key and its matching private key are meant to be reused continuously, not regenerated for each release.

The bundle build number in both Build and Release defaults to the Unix committer timestamp of the source commit, which avoids the discontinuous run numbers of the individual workflows. A stable release first requires its semver to be greater than the current latest; where an appcast already exists, the new build must also be greater than every item in it. A prerelease produces no stable appcast and never becomes latest. Only the original 0.1.0 is allowed to have no appcast; if a later latest is missing that file, release validation refuses it, so the build ordering constraint cannot be skipped.

## DMG install layout and the limits of Apple signing

`make-dmg.sh [release-version]` produces `app/dist/Tursora-<version>-macOS-arm64.dmg` from the verified app; on this machine `TURSORA_PYTHON=/opt/homebrew/bin/python3.13` selects the Python to use. The minimum is Python 3.10 and CI uses 3.13; a separate `.build/dmg-tools` venv pins dmgbuild 1.6.7, ds-store 1.3.3 and mac-alias 2.2.3, and the SHA-256 of every wheel is committed to the repository and enforced.

The image is a compressed read-only HFS+ volume with a 640 × 280 window and 128 px icons written in advance; Tursora sits at `(140, 120)`, Applications at `(500, 120)`, and an arrow background sits between them. The `Applications` symlink points at `/Applications`. The MIT license for the background is kept in a hidden file at the root of the volume and is not placed inside the signed app. The build script writes `.DS_Store` directly and does not rely on the Finder UI; after mounting read-only it checks the bundle signature, the platform, the update metadata, the symlink, the license and the layout, and then unmounts.

The number of valid code-signing identities on this machine is 0, and the user confirms there is no Developer ID yet. No Apple signing script is added for now, because it could not be verified; once the membership, the Developer ID Application certificate and private key, and the notarization credentials are in place, hardened runtime, notarization and stapling will be wired in and verified. The Mac App Store additionally involves App Sandbox and distribution design, which is separate work for later. Neither the Sparkle signature nor the DMG container can take the place of Apple notarization.

For the maintenance steps see [RELEASING.md](../RELEASING.md). The update signature is not a substitute for Developer ID signing or notarization; the app today is still ad-hoc signed and not notarized.

## First launch today: actual writable locations and targeted attribute handling

The user reported that an ordinary account cannot approve the app in System Settings, and asked for different install locations to be covered. The [current guide](../../site/install.md) chooses a path according to an existing installation, whether Homebrew is actually available, and the writable directory the user picks; `/Applications`, `~/Applications` or another directory all work, and no single destination is required. A DMG copy is first checked against the official SHA-256 for the same version and only then copied to the chosen location; the read-only image must not be modified and an app of the same name must not be silently overwritten. Homebrew keeps the full URL → single-cask trust → install order, and a directory of the user's own choosing is given with `--appdir`.

Where the quarantine from a first download has to be dealt with, `xattr -dr com.apple.quarantine "$app_path"` is run only on a copy that is actually trusted; no `sudo` and no global policy command is used. The local macOS `man xattr` remains the evidence that `-d` names the attribute and `-r` sets the recursive scope. Rascal's current README uses `-cr`, which clears every extended attribute; Tursora keeps to the narrower scope. [Apple DTS](https://developer.apple.com/forums/thread/813858) confirms that a downloader adds quarantine in order to trigger Gatekeeper; that is the basis for explaining how a locally compiled build and a downloaded copy can differ, and "it runs locally" is not taken to mean it is notarized. An ordinary account's own writable files and organizational policy are handled separately; [Apple device management](https://support.apple.com/en-euro/guide/deployment/dep61dc030/web) can restrict a user's ability to approve an app, so the targeted attribute command cannot be guaranteed to solve every managed device. Reading the guide is not by itself authorization to install or launch anything; an agent needs a matching request from the user already.

This round was documentation and a check of primary sources; no attribute change was made to the user's app on the strength of it, and no new on-device test of an ordinary-account install or a first Gatekeeper prompt was added. The released binary, the signature, the version and the scope of the historical tests stay as they were.

## Earlier first-launch instructions (2026-09-13, historical)

At the user's request the [Rascal download instructions](https://github.com/chang-07/rascal#download) were used as a reference, adopting the order download → open the DMG and drag into Applications → launch from Applications. When the first-launch instructions were written, Tursora's official release was still the `0.1.0` ZIP, and the README and the website honestly kept the transitional wording; after 0.2.0 was released that wording and the real Homebrew tap were updated, see the top of this page. Rascal's own [cask](https://github.com/chang-07/homebrew-tap/blob/main/Casks/rascal.rb) puts the ad-hoc / unnotarized status and the quarantine-attribute handling in `caveats` and does not run that command automatically in an install hook; its way of distributing is not evidence that Tursora is signed or notarized.

[Apple's "Safely open apps on your Mac"](https://support.apple.com/en-us/102445) (page dated 2026-05-27, read on 2026-09-13) gives this order for a single app: try to launch it, then go to System Settings → Privacy & Security and choose Open Anyway, and choose Open in the confirmation prompt. The precondition is that the user is confident the source is trustworthy and has not been tampered with. The README made that the main path at the time, and the website carried only a short note plus a link to the README's `#first-launch`, without extending the static builder's external-link allowlist. The prompts about a developer who cannot be verified and about malware that cannot be checked for are not a single explanation for actual malware detection, revoked authorization or file corruption; corruption is handled by downloading again and checking the checksum for the same version first, and a malware warning is not treated as an ordinary quarantine-attribute problem.

The local macOS `man xattr` states plainly that `-d` deletes the extended attribute with the given name and `-r` processes the contents of a directory recursively. The collapsed terminal alternative in the README therefore uses `xattr -dr com.apple.quarantine /Applications/Tursora.app` rather than copying Rascal's `-cr`. The precondition for running it is that the source is an official release and matches the `SHA256SUMS.txt` of the same version; all it does is remove that app's download quarantine attribute — it grants neither Developer ID nor notarization, and it repairs no corruption. This round only read the man page and wrote the instructions: no quarantine-attribute command was run, no system security setting was changed, and no first Gatekeeper block was tested on the device; the existing scope of 77 Swift sources, the 2,158 × 3 smoke runs and the on-device test of a normal update is not widened by it.

After the instructions were changed, the static build, the documentation links and `git diff --check` all passed; a real browser check of the download section at desktop width and at a 390 px viewport showed the steps and the first-launch link fully readable with no horizontal overflow. For the exact scope see the [Pages record](github-pages.md).
