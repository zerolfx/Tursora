# Search input and criteria entry points compared (2026-09-12)

This record checks the pinned Dolphin source in this repository and Apple's official documentation, and records the unified Tursora search entry point implemented in this round. The Dolphin checkout is `5e457ee9e88aa6277fbf056cd5c32462c5318866`, and the working tree was clean when it was read; Dolphin was not run, and no claim of completed visual verification is made on that basis. The text below separates upstream facts, Tursora's product choices and the implementation status; the last section records the packaged-application screenshot stage that followed the 2,024-check test run, and the final results of the later Dock / input method adjustment stage are in the [Dock research record](dock-menu.md). The existing backend and the historical verification scope are in [search.md](search.md) and [search-verification.md](search-verification.md).

## How Dolphin actually behaves: typing runs the search, the button expands the criteria

In the pinned version, the first row of `Search::Bar` is, in order, the search input, the `Filter` button and the close button; there is no separate `Search` execute button. The input field carries its own clear action, and a save-search action sits at its trailing end; `Filter` uses `InstantPopup` to open the criteria menu, whose purpose is to modify the query. The second row shows the `Here` / `Everywhere` scope and the criteria currently selected. Evidence: [bar.cpp:53–163](https://invent.kde.org/system/dolphin/-/blob/5e457ee9e88aa6277fbf056cd5c32462c5318866/src/search/bar.cpp#L53).

| Input or action | Behaviour in the pinned source |
|---|---|
| Editing the search term | Restarts a single-shot timer; submits the current configuration 500 ms after typing stops |
| Return | Stops the pending timer, submits immediately, and requests that focus move to the results view |
| Changing the scope, the search method or the criteria | Submits as soon as the configuration changes, with no separate execute button to press |
| Escape | Clears the search term when there is one; closes the search bar when the term is already empty |
| Both the search term and the effective criteria are empty | Returns to the location from before the search started, avoiding an unconditional scan |
| Only effective criteria such as type | The indexed backend can still run the query; a search term is not required |

Evidence: [bar.cpp:38–44](https://invent.kde.org/system/dolphin/-/blob/5e457ee9e88aa6277fbf056cd5c32462c5318866/src/search/bar.cpp#L38), [bar.cpp:279–332](https://invent.kde.org/system/dolphin/-/blob/5e457ee9e88aa6277fbf056cd5c32462c5318866/src/search/bar.cpp#L279). Return here means "run it now and go to the results", which is not the same as opening the first result.

The criteria popup contains the file name / content search methods; a build that includes Baloo also offers the simple search / file index backends, along with the type, modification date, rating and tag selectors. The backend and the availability of an index affect whether options are enabled and whether they are shown at all. This therefore cannot be generalised into "all Dolphin criteria are available in any directory". Evidence: [popup.cpp:72–105](https://invent.kde.org/system/dolphin/-/blob/5e457ee9e88aa6277fbf056cd5c32462c5318866/src/search/popup.cpp#L72), [popup.cpp:107–243](https://invent.kde.org/system/dolphin/-/blob/5e457ee9e88aa6277fbf056cd5c32462c5318866/src/search/popup.cpp#L107), [popup.cpp:273–319](https://invent.kde.org/system/dolphin/-/blob/5e457ee9e88aa6277fbf056cd5c32462c5318866/src/search/popup.cpp#L273).

Type, date, rating and tags that are already in effect appear in the main search bar as editable, removable criteria chips, wrapping onto another line when there is not enough width; the whole criteria form does not have to stay expanded. Evidence: [bar.cpp:240–276](https://invent.kde.org/system/dolphin/-/blob/5e457ee9e88aa6277fbf056cd5c32462c5318866/src/search/bar.cpp#L240), [chip.h](https://invent.kde.org/system/dolphin/-/blob/5e457ee9e88aa6277fbf056cd5c32462c5318866/src/search/chip.h), [barsecondrowflowlayout.cpp](https://invent.kde.org/system/dolphin/-/blob/5e457ee9e88aa6277fbf056cd5c32462c5318866/src/search/barsecondrowflowlayout.cpp).

**Difference from what the user asked for:** Dolphin's `Filter` entry point is already there when the input is empty; the source has no condition of "the entry point only appears once something is typed". Tursora offering the expansion entry point after typing is a layout choice that follows the user's request for this round, and must not be written up as an exact reproduction of Dolphin.

## Do not confuse the standalone Filter Bar with Search's criteria button

Input in Dolphin's standalone `FilterBar` triggers `filterChanged` directly, along `DolphinViewContainer.setNameFilter` → `DolphinView.setNameFilter` → filtering the current model; it filters names within the current view and is not responsible for starting a recursive search. It has options for keeping the filter, for case sensitivity and for text / glob / regular expression modes. The `Filter` inside the search bar instead opens the search criteria popup described above and changes the recursive search request. Evidence: [filterbar.cpp:26–78](https://invent.kde.org/system/dolphin/-/blob/5e457ee9e88aa6277fbf056cd5c32462c5318866/src/filterbar/filterbar.cpp#L26), [dolphinviewcontainer.cpp:112](https://invent.kde.org/system/dolphin/-/blob/5e457ee9e88aa6277fbf056cd5c32462c5318866/src/dolphinviewcontainer.cpp#L112), [dolphinview.cpp:681](https://invent.kde.org/system/dolphin/-/blob/5e457ee9e88aa6277fbf056cd5c32462c5318866/src/views/dolphinview.cpp#L681).

In the same way, Dolphin's `Everywhere` cannot be taken over directly as the name for Tursora's Home scope: the former starts from the filesystem root on the simple search backend and covers the indexed locations on the indexed backend, whereas Tursora's `SearchRequest.effectiveRootURL` explicitly picks only the current starting point or the current user's Home. The wording of the scope should let the user know where the search actually looks. Dolphin evidence: [bar.cpp:222–239](https://invent.kde.org/system/dolphin/-/blob/5e457ee9e88aa6277fbf056cd5c32462c5318866/src/search/bar.cpp#L222); local evidence: `effectiveRootURL` in `app/Sources/Tursora/Model/SearchRequest.swift`.

## Spotlight: querying an existing index is not the same as reading a file's contents

Apple's `NSMetadataQuery` queries Spotlight metadata through a predicate and a search scope. The initial phase queries the existing Spotlight store and sends `NSMetadataQueryDidFinishGathering` when it is done; the API also supports a subsequent update phase. Giving a directory URL limits the scope of the results — it does not thereby read every file in that directory on the spot, nor does it automatically guarantee that the contents are in the store. The first two sentences are documented API behaviour; the last one is a usage boundary inferred from "it queries the existing store". Evidence: [Apple: Querying Metadata, Limiting the Search Scope / Running the Search](https://developer.apple.com/library/archive/documentation/Carbon/Conceptual/SpotlightQuery/Concepts/QueryingMetadata.html), [NSMetadataQuery](https://developer.apple.com/documentation/foundation/nsmetadataquery).

An importer for a file format can supply a text representation of the file's contents to `kMDItemTextContent`, which applications then query. Apple states explicitly that this attribute can be queried but that its value cannot be read out directly; so seeing that field empty in `mdls` is not on its own proof that a file's contents have not been indexed. Evidence: [Apple: Assigning Values to Metadata Attributes](https://developer.apple.com/library/archive/documentation/Carbon/Conceptual/MDImporters/Concepts/AssigningDataToAttrs.html).

Users can also exclude directories or disks in the system's Spotlight Search Privacy settings. Whether content can be matched depends on whether the current index holds searchable text, on format support and on the scope / exclusion conditions; "the file exists" or "indexing is enabled for the disk" must not be taken as proof that a particular file's contents are already queryable. The exclusion mechanism comes from [Apple: Prevent Spotlight searches in specific folders or disks](https://support.apple.com/en-gb/guide/mac-help/mchl1bb43b84/mac); the boundary on judging whether a particular file is in the store is an inference from the APIs above.

How Tursora's backend actually divided the work when this was written:

- With no content criterion, a background filesystem traversal does the recursive name, type and date matching; name search does not depend on the Spotlight index.
- When the content criterion is non-empty, `usesSpotlight` selects `NSMetadataQuery`, the content criterion is bound to `kMDItemTextContent CONTAINS[cd]`, and the scope is the request's actual starting URL. There is no fallback that reads the contents file by file, and there is no full-text index built by Tursora.
- Once the initial gathering has finished it calls `stop()` itself, copies the paths in batches and checks that the files still exist, are still in scope and still meet the metadata criteria, forming a single snapshot of results. That the API supports live updates does not mean Tursora has adopted live updates.

Local evidence: `usesSpotlight` / `metadataPredicate` in `app/Sources/Tursora/Model/SearchRequest.swift`; the backend selection and `beginQuery` / `gathered` / `copyPaths` in `app/Sources/Tursora/Model/SearchBackend.swift`. The 30-second timeout, examining at most 50,000 Spotlight candidates, and re-running after a snapshot ends are all Tursora implementation choices, not fixed limits of the Apple API.

## Tursora's settled choices and implementation for this round

The user confirmed using a single input field: it filters the current folder first, and once something is typed it offers an entry point to detailed search. The implementation has removed the separate toolbar Search button and the Search execute button inside the panel; the visible name editor is always the original toolbar input field. With an empty filter term there is no extra panel; once text is typed, `Current Folder` and `Search Options…` are shown in the owning pane. Clicking it keeps the typed term and expands the content / scope / type / date criteria; ⇧⌘F still expands directly when the input is empty. Once expanded, a persistent criteria panel is used and Close leaves the search — this is not a reproduction of Dolphin's criteria popup and criteria chips.

| State or action | Behaviour Tursora has implemented |
|---|---|
| Ordinary typing | Filters the current list immediately and supports `*` / `?`; does not start the recursive backend |
| Expanding Search Options | The input becomes a recursive name criterion; the original text is kept and matched as a literal substring, glob is not converted into a query expression; the placeholder changes from Filter by Name to Search by Name |
| Editing the name or the content, or adjusting criteria | Consecutive changes are coalesced and queried automatically after 500 ms; Return in the name field runs the query immediately and hands focus to the file view, while an automatic run keeps the editing focus |
| Input method composition | While the name / content field still has marked text, the pending automatic query is cancelled; once the composition is committed the query is scheduled again |
| All criteria empty | Clears the request and the results and does not start an unconditional recursive scan; opening an empty saved search goes through the same protection; a query is still possible when content / type / date alone are effective |
| Clearing and leaving | Clear empties the criteria, the results and the request while keeping the scope and the expanded panel; the toolbar cancel button / Escape explicitly leaves the search and returns to the directory; an empty name merely losing focus keeps a content or type search |

The scope, the draft, the timer and the SearchSession all belong to the pane; the window toolbar shows only the current state of the active pane. Switching panes / tabs does not hand a pending query over to the new active pane. Navigating, leaving and closing cancel the pending timer; when a closed tab is reopened, if the kept draft differs from the submitted request the query for that pane is scheduled again. A filter term kept while navigating within the same directory also shows the detailed entry point again.

The implementation also distinguishes AppKit's first search event from state synchronisation: the first edit is written to the owning pane first, so that when the system sends the search-started notification first, it cannot overwrite the characters just typed with the old empty value. Open on a saved search goes through the unified submit path, which validates the dates and the empty-criteria case; the refresh for file operations during a search still uses the request the owning pane has submitted, keeping the real URL and the existing selection / generation rules.

The tooltip for the content criterion and the content query status explain in plain words the macOS index, the supported formats and what is missing when something is unindexed / excluded; the ordinary name filter shows no index limitations. It can be summarised for the user as: "Names are looked up in the folder and its subfolders; content uses the macOS Spotlight index and can only find content the system has already indexed and supports." No results, a failed start and a timeout are still distinct states.

Local implementation: the single toolbar field and its delegate in `MainWindowController.swift`; the owning-pane routing in `BrowserSearch.swift`; the criteria panel, the 500 ms timer and the handling of empty criteria and input method composition in `SearchPanelController.swift`; the close and reopen paths in `TabsController.swift` / `TabPage.swift`. The unified entry point and the boundaries above have been added to `SearchEntrySmokeTests.swift`, and the original search backend / file operation cases are kept.

## Verification status for this round

At the screenshot stage, before this round's Dock work and the later input method adjustment, the full smoke on the combined source **passed three consecutive rounds, 2,024 checks each**, all three exiting 0 with empty stderr; this is the total for the combined suite, including the regression for the unified search entry point. The tests cover the single visible input field, both file views, automatic submission and immediate execution, the empty-criteria protection, cancellation, pane / tab draft isolation, the same-directory hint, and the draft after a tab is closed and reopened.

The release build passed at that screenshot stage, with the log at `/private/tmp/tursora-tabs-appearance-verification/release-final.log`; the root task confirmed that strict codesign, the Info.plist lint and the in-bundle icon consistency check passed. Under the real system's dark appearance and an app-process-only light appearance, the same single toolbar input field was actually used to type `Notes` in the Delivery pane: it first filtered the current directory, Search Options appeared, and expanding it automatically produced one `Release Notes.md` result. The content of the Design pane on the other side was unaffected. The native cancel button `×` returning to the directory, and Escape leaving the search, were also actually performed. The window was resized from its initial width of 560 px to 1200×720; the search flow and the final screenshots were done at the latter, and no claim is made on that basis that every narrow-window search state was tested.
